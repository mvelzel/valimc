# VMC-069 — Connection hot path and decomposition

Status: Done
Milestone: M1 foundations
Depends on: none (parallel with the world tickets).

`Valimc.Connection` is a 5,800-line process holding socket I/O, codec, login,
play dispatch, movement, vitals, mining, menus, crafting, replication and
persistence. The audit also found per-tick costs that grow with nearby players.

## Stage B: hot-path fixes (this checkpoint)

- **Slim peer views.** `Players` publishes `{pid, view, replica}` rows: the 22-word
  replication view and a ~15-field replica. Each tick, known peers cost one view
  lookup when unchanged; the replica is read only when a view changed and the
  full player map only for a newly visible peer (293 → 22 words per peer-tick).
- **Frame once.** Broadcast player packets are framed/compressed by the sender and
  shared as one refc binary; recipients only encrypt.
- **Counters.** `Metrics` uses one write-concurrent `:counters` cell per key. Ten
  processes incrementing one key 2M times in compiled code: ETS `update_counter`
  37.9 s versus `:counters` 5 ms.
- **Packet ids.** `Data.id/3` and `Data.name/3` are compile-time function clauses
  instead of nested JSON map lookups (162 → 54 ns per outbound packet); registry
  ids use a compiled index instead of a linear scan. Integer `handle_packet`
  dispatch was measured unnecessary (inbound name lookup is 66 ns) and dropped.
- Earlier in this milestone: logged exceptions, graceful overload shutdown with a
  kill fallback, vanilla chat throttle, ready-pid broadcast selection, partitioned
  collision pool and snapshot block reads ([VMC-065](VMC-065.md)).

Measured but not changed: reusing one zlib stream per process saves about 20%
per compressed packet (15 → 12 µs for 4 KB); not worth the state yet.

## Stage A: decomposition (next)

Target modules (line ranges at `3f437d1`): `Net.Codec` (socket, framing, crypto,
rate windows, outbox), `Net.LoginFlow` (handshake → configuration), `Net.Serverbound`
(integer packet dispatch with compile-time ids), `Session.Jobs`, `Session.Effects`,
`Session.Replication`, `Session.Persistence`, `Player.Movement`, `Player.Vitals`,
`Player.ItemUse`, `Player.Mining`, `Player.Placement`, `Player.Menus` and
`Player.Transfers`; the shell keeps init, the callback wrapper, the consume loop,
tick orchestration and terminate (~600 lines). `socket`, `phase`, `player` and
`inventory` stay top-level; other keys move into per-module sub-structs.

`Session.Jobs` replaces nine hand-rolled job lifecycles (pose, pickup, mining,
placement, motion, experience, table/container, key/auth, recovery delivery):
`start/attach/classify/take/cancel/cancel_all`, one `{:job_timeout, kind, ref}`
message and one dispatch clause; per-kind semantics (motion retry gating, placement
serialization, multi-stage experience/table jobs, auth deadline re-check) stay in
the owning domain module.

Steps (one commit each, all socket suites green):

0. `test/support` accessor (`ConnState.peek/replace`) mapping legacy flat keys to
   nested paths; codemod `:sys.get_state`/`replace_state` in the socket tests.
2. Per-turn outbox: one coalesced `gen_tcp.send` per callback, early flush at the
   write-batch cap, flush before cipher changes.
3. `Session.Jobs` with unit tests; 4a–i migrate each job kind.
5–13. Extract Codec, LoginFlow (+ effects applier), Serverbound, Replication
   (golden byte tests), Movement, Vitals/ItemUse, Mining/Placement, Menus,
   Transfers/Persistence (minimal; VMC-064 rewrites transfers).

Risks: cipher/compression transitions with a buffered outbox, oversized
coalesced writes, publish-before-deliver ordering, exception paths with a
buffered outbox, guard rewrites (`is_map_key ... and`), and long line-range
moves conflicting with parallel work (land steps quickly).

Progress (October 19, 2026): `Session.Jobs` is in place and `handle_info` offers
every message to it first. Pose, pickup, mining, placement, motion and experience
jobs are migrated (their result/deadline/DOWN/cancel clauses and terminate blocks
are gone). Table/container and recovery-delivery jobs move with the VMC-064
transaction engine and key/auth jobs with the login-flow extraction, rather than
being migrated twice. Socket tests read connection state through
`Valimc.TestConn`, which keeps legacy job views.

Checks: socket suites pass after each migration (560 tests on the last full run).

Acceptance: socket suites pass; replication and broadcast packets byte-identical;
benchmark of co-located peers shows the per-tick copy reduction.

Stage A result (October 20, 2026): `Valimc.Connection` went from 5,758 to 498
lines: the GenServer shell (init, calls, the consume loop and terminate). The
rest moved, unchanged in behaviour, into `Net.Codec`, `Net.LoginFlow`,
`Net.Serverbound`, `Session.Messages` (message routing), `Session.JobHandlers`,
`Session.Events`, `Session.Replication`, `Session.Commands`, `Player.Movement`,
`Player.Vitals`, `Player.ItemUse`, `Player.Mining`, `Player.Placement`,
`Player.Menus`, `Player.CreativeInventory` and `Player.Transfers`. The split was
mechanical (a one-off extraction script: moved functions become public, calls are
qualified, module attributes and guards copied, unused aliases pruned from
compiler warnings), so the full suite (1,583) passes unchanged.

Not done, by decision: the table/container, key/auth and recovery-delivery
lifecycles stay bespoke rather than moving onto `Session.Jobs`. They are
multi-stage and the consume loop and inventory guards inspect them directly, so
the migration would only rewrite guards. The per-turn outbox (step 2) was not
pursued: replication already buffers through `outbound`, and no measurement
shows send syscalls mattering.

M1 milestone client run (October 20, 2026, `127934a`, frozen release, survival and
creative datasets): join, chat and commands; survival mining, pickup and pillar
placement; creative stone, slab doubling, log axis from the clicked face, chest and
furnace facing; 30-item drops, merges and pickups; chest fill, rapid shift-clicks,
creative spill; furnace smelting with output collection; walk, sprint, flight,
fall damage, hunger, death and respawn; reconnect and server restart in both
modes. All matched vanilla with clean logs (`.local/client-tests/M1/`). Limits:
creative double-tap flight stop was inconsistent (client-side, likely the input
bridge); XP orbs were not observable in creative. Both were resolved in the
VMC-066 run: held taps stop flight 5/5, and survival smelting showed orb XP.
