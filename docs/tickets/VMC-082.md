# VMC-082 — SIMD where data-parallel work dominates

Status: Planned
Milestone: M3, at the user's request

No Rust code uses SIMD explicitly, and the release build targets baseline
x86-64 (SSE2), so the compiler cannot vectorize with AVX2 where loops would
allow it. Most simulation is branchy per-entity logic that SIMD does not
help; the gains are in work that runs the same arithmetic over many
independent cells.

## Candidates, by expected gain

1. **Terrain noise and density functions** (`worldgen::noise`, `density`,
   `sampler`, `terrain`, `climate`). Terrain is most of a chunk's generation
   cost (27 to 54 ms a terrain job on the VPS in captures 11 to 14) and
   evaluates Perlin octaves, splines and density trees per cell, thousands
   per chunk. Evaluating 4 or 8 cells per lane is the classic case; expect
   two to four times on the noise part.
2. **Biome climate search** (`worldgen::climate`): the parameter-space
   distance over every candidate point per biome lookup.
3. **Light propagation** (`light`, `light_grid`): section-wide initial light
   and edge passes over nibble arrays.
4. **Section data** (`section`, palette packing and unpacking, heightmap
   scans) and chunk packet encoding.
5. **Not candidates:** mob AI, pathfinding and block rules (branch-heavy,
   per-entity); compression stays in its library.

## Approach

- First, the build target: the image is built on the VPS, so the release
  build can target its instruction level (x86-64-v3: AVX2, BMI, FMA)
  after checking the CPU flags. Rust never contracts `a * b + c` into a
  fused multiply-add on its own, so results stay bit-identical; this is a
  build change measured on its own.
- Then explicit SIMD on stable Rust with the `wide` crate (pure Rust;
  portable `f64x4`, `f32x8`, `i32x8` types; SSE and AVX on x86, NEON on the
  development Mac, scalar elsewhere). `std::simd` is nightly-only; moving to
  it once it stabilizes is mechanical. `std::arch` intrinsics only where
  `wide` lacks an operation, behind runtime detection with a scalar
  fallback.
- **Exactness.** Generated chunks must stay bit-identical to vanilla's. Lane
  arithmetic rounds exactly as scalar arithmetic does; transcendental and
  table functions (`Mth.floor`, lerps, spline evaluation, `java.rs` math)
  keep their scalar definitions per lane or a proven-equal vector form.
  Branches per cell become masks evaluated in the scalar order where order
  matters.

Acceptance:

- Every worldgen vanilla stage passes unchanged (terrain, biomes,
  decoration, live generation, structures, datapacks).
- Matched benchmarks before and after, on the VPS's instruction level and on
  two pinned cores: `bench/worldgen_terrain.exs` and `bench/worldgen_live.exs`
  against vanilla and Pumpkin as in [VMC-024](VMC-024.md) and
  [VMC-025](VMC-025.md); the 081a `explore` scenario's chunks per minute.
- Each candidate lands only with a measured gain; a candidate that does not
  pay is recorded here and dropped.

Order: after [081d](VMC-081d.md). The build target first, then terrain
noise, then the others by measured share.
