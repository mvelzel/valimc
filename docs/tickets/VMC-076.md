# VMC-076 — Fast feedback: cached oracles, test tiers, bounded heavy work

Status: In progress
Milestone: tooling (precedes M3)
Depends on: none.

Sessions spend most of their time running or waiting for checks: in October
2026 roughly a fifth of a session's work was reading and writing code and the
rest was tests, oracles and benchmarks, or waiting for other sessions' runs on
an overloaded 10-core host (load averages of 40–70 were common). This ticket
records the audit of every check the workflow runs and the plan to make the
everyday loop cheap, run heavy checks rarely, and keep them from overlapping.

## Audit (October 21, 2026; main at e2c81e8)

Measured on the development Mac (10 cores), some under load as noted.

| Check | Cost now | What drives it |
|---|---|---|
| Rust rebuild after a one-line change (`valimc_core`) | 64 s (17 s with the dev profile below) | release profile with thin LTO and one codegen unit, used for every build, dev and test included (`use Rustler … mode: :release`) |
| Rust build in a fresh worktree | about 4 min (54 s with the dev profile) | the same; 19 worktrees each hold their own `native/target` (about 9 GB in all) |
| Elixir full compile | 18 s (40 s CPU) | fine; `version.ex` and the block registry recompile 43 and 22 files |
| Java oracle compile | about 7 s for all 211 sources | fine; but any edit recompiles all, mtime-only stamp |
| `mix test.fast` | about 30–60 s | `--exclude tcp` only: live-worldgen modules (proto owners, decorated worlds, structure flags, item portals) still run in it |
| `mix test` | 312 s, 297 s of it in serial modules | 70 `:tcp` modules (547 tests) of real sockets, and seven live-worldgen and portal modules; the top 60 modules take 204 s (proto owner 28 s, player use 19 s, mining 11 s, motion 10 s) |
| `check_vanilla.py` (226 stages) | 39 min wall, 11,600 stage-seconds; 39–107 min observed in worktrees | 284 JVM and 228 BEAM launches; the top 12 stages are 53 % of the time; vanilla's side (Java) is about 5,200 s and deterministic, rerun from scratch every time |
| Fact regeneration inside the parity run | about 2,400 s | `worldgen_survival` 986 s, the `shapes.json` part of `worldgen_shapes` about 690 s, `support.json` part of `support`, `worldgen_facts`: they change only with the pinned jar or the extractor |
| Benchmarks | minutes each; heavy ones (live generation, fresh terrain, `load.py`) were repeated in pairs | not gated, but run concurrently with oracles on a loaded host, so results needed reruns (load 11–70 recorded) |

Process findings:

- `AGENTS.md` asks for the full `mix test`, full `check_vanilla.py` and a
  release build at every parent-ticket boundary; `docs/development.md` says
  once per milestone and quotes stale durations (30 s, 100 s, 15 minutes).
  Several sessions ran the full gates many times a day each, concurrently.
- `check_vanilla.py --only` matches substrings (`place` runs 11 stages,
  `worldgen` 28), silently passes when nothing matches, and always skips TCP;
  stages run first-in first-out, so the longest start last; the all-core
  oracles (support, shapes, decoration) run beside four other stages.
- Duplicated work: two dedicated-server runs are generated twice per run
  (`ChunkOracle generate`, `AnvilContentOracle generate`), the terrain oracle
  recomputes fill three times, `damage_protection_1..9` and
  `player_crafting_1..3` are one oracle split into fresh JVMs and BEAMs,
  `SupportOracle` refines all 35,723 states twice (`support` and
  `worldgen_survival`), and `ShapeOracle` scans ValiMC's Rust sources, so every
  worldgen edit invalidates an 11-minute regeneration.
- Tests: the suite holds few outright duplicates (about 59 tests across 12
  files: furnace-kind and hand loops, mode-immunity loops, nine "malformed
  packet disconnects only the sender" tests, the clock, weather and difficulty
  connection tests, the permits family, creative-slot files). Its cost sits in
  a few heavy modules: live world generation, real-time waits (mining ticks,
  rain ramps, item ageing, eating) and fixed sleeps in socket tests.

## Plan

Each phase is its own slice; the order follows payoff.

A. Bounded everyday loop (small, immediate)
- A dev and test Rust profile: no LTO, 16 codegen units, incremental, passed
  through Rustler's `env`; `prod` and benchmarks keep the full profile.
- One machine-wide gate for heavy work: `scripts/heavy` takes one of a few
  slots (a `flock` semaphore in the main checkout, default 2) and runs the
  command at low priority. `check_vanilla.py`, full `mix test`, release builds
  and benchmarks take a slot; sessions queue instead of overloading the host.
- Test tiers: `@moduletag :slow` on the live-worldgen and portal modules;
  `mix test.fast` excludes `:tcp` and `:slow`; `mix test.all` includes
  everything for milestone gates.
- `check_vanilla.py`: exact `--only` (globs explicit, zero matches fail),
  `--only tcp`, longest stages first from persisted timings, all-core oracles
  capped to their share of the cores.
- The workflow written down once (AGENTS.md, development.md): per commit,
  format and `mix test --stale` (and `cargo test` for Rust); per parent ticket,
  `mix test.fast` and the stages that change touches; per milestone, the full
  gates; per version bump, regeneration. Benchmarks only for tickets whose goal
  is performance, under a heavy slot on a quiet host.

B. Cached oracles and change-based stages (the largest lever)
- Cache each oracle's output by content: pinned jar, JDK and flags, the
  oracle's transitive Java sources, its arguments and the repo files it reads;
  one cache shared by every worktree. A stage then reruns only ValiMC's side
  (and the verify steps that read ValiMC output).
- A regeneration tier (`--regen`) for fact extraction; the parity run checks
  that committed facts match the cached extraction instead of re-deriving them.
- `--changed [REV]`: the stages a diff touches (triggers per stage, the Elixir
  xref closure, the Java helper closure and native module families).
- Merge the fragmented and duplicated stages listed above; run many checks in
  one BEAM; move `directory_recovery` into ExUnit and `inventory_behavior` into
  the regeneration tier; decouple `ShapeOracle` from ValiMC's Rust sources.

C. Test suite cleanup
- Delete or merge the duplicates (about 59 tests, 12 files).
- Replace real-time waits with manual ticks and explicit expiry; make the four
  modules marked serial before VMC-073 async and split the global-state tests
  out of otherwise pure modules.
- Optional: consolidate about 60 one- or two-test files; drop pre-M2 save
  format readers and their tests if old development worlds need not load.

D. Cheaper JVMs and benchmark hygiene
- A JDK AOT or class-data archive for the oracle classpath; a batch runner for
  cache misses; per-class `javac` into a class directory shared by worktrees.
- Retire `worldgen_live_trace.exs`; prune ad-hoc results; benchmarks always use
  the full release profile.

Acceptance:

- A one-line Rust change rebuilds in under 20 s for tests; a new worktree
  builds the NIF in about a minute.
- `mix test.fast` stays under 30 s; the full suite under 150 s.
- With a warm cache, a typical change's oracle stages finish in a few
  minutes, and the full parity run (all stages, no regeneration) in under
  15 minutes.
- No more than two heavy jobs run at once on the host, whichever sessions
  start them.

## VMC-076a — fast NIF builds and heavy-job slots (October 21, 2026)

- Dev and test builds pass Rustler `CARGO_PROFILE_RELEASE_LTO=false`,
  16 codegen units and incremental compilation, with
  `CARGO_TARGET_DIR=native/target/fast` (`config/config.exs`), so they never
  evict the full-profile artifacts. `prod` and the new `bench` Mix env
  (`config/bench.exs`, the dev configuration) keep `native/Cargo.toml`'s full
  release profile in `native/target`.
- Measured at load 2–14: the first fast build of a checkout 25 s; a one-line
  `valimc_core` edit 4.7 s in test; switching dev to the new profile with a
  further edit 15.7 s (Elixir included). The full-profile bench build of the
  same tree reused `native/target` (48 s, mostly dependency and Elixir compiles).
- `scripts/heavy.py CMD…` takes one of `VALIMC_HEAVY_SLOTS` (default 2) flock
  slots in the main checkout's `.local/heavy/`, shared by every worktree, and runs
  the command at niceness 10; waiting jobs print who holds the slots, `--status`
  lists them, nested calls (`VALIMC_HEAVY_HELD`) take no second slot, and TERM
  or HUP reaches the command. Checked: a second job waits for the first, a nested
  call runs, the exit code passes through, TERM stops the command and frees the
  slot.
- `mix test.fast` excludes `:tcp` and `:slow`; AGENTS.md and
  `docs/development.md` scale checks with the change (affected tests per commit,
  `test.fast` per parent ticket, full gates per milestone, heavy commands through
  the slots, benchmarks only for performance tickets under `MIX_ENV=bench`).

## VMC-076b — exact stage selection, longest-first scheduling (October 21, 2026)

- `check_vanilla.py --only` takes exact stage names, comma-separated or repeated;
  only a name with `*`, `?` or `[` is a glob. A name that matches nothing exits 1 and
  suggests close names (`pose_fit` → `player_fit`). Before, `place` ran 11 stages,
  `worldgen` 28, and `pose_fit` (the documented example) ran none and passed.
- The TCP oracle is the stage `tcp`: it runs in the pool with the others, alone with
  `--only tcp`, and is left out by `--skip-tcp` or an `--only` that does not name it.
  Its client JVM now gets the same intrinsic flags as every oracle.
- Stages start longest first. Each run merges its stage durations into the main
  checkout's `.local/oracle-cache/timings.json` (locked, atomic replace), shared by
  every worktree; stages without a measurement use `ESTIMATES` in
  `vanilla_stages.py` (the audit's figures), else 15 s. `--list` shows them.
- `SupportOracle` and `ShapeOracle` (`THREADED`) run one at a time with
  `-XX:ActiveProcessorCount` = cores − jobs + 1 (6 on ten cores at five jobs), so a
  run plans at most one thread per core instead of two all-core pools beside four
  other stages.
- A run of more than six stages takes a heavy-job slot itself (`heavy.acquire`,
  niceness 10) unless `VALIMC_HEAVY_HELD` says it already holds one. Checked: a
  nine-stage glob run held slot 0 (`heavy.py --status`), `--only player_fit,tcp`
  took none and passed in 28 s.
- A worktree without its own `research/vanilla-bundle` or `.local/toolchains/jdk`
  uses the main checkout's, so a fresh worktree needs no second jar extraction.

## VMC-076f — pruned inventory, cooking and item tests (October 21, 2026)

Audit areas C (inventory, containers, crafting), D (cooking, furnace, XP) and E
(items and entities), plus the creative-component connection files and
`mining_permits_test`. Rule applied: one socket golden path per player-visible
family, one atomicity or recovery test per feature on top of the engine's own
tests, untrusted-input boundaries; vanilla facts go to their oracle stages.
Save-format version tests stay for VMC-076g.

|---|---|---|---|
| C (with the permits merge and creative files) | 60 → 42 | 272 → 115 | 10,082 → 5,696 |
