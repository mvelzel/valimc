# VMC-034n3 — Owned XP orb materialization

Status: In progress. Depends on [pending awards](VMC-034n2.md); part of [earned output](VMC-034n.md).

Current slice: unused materialization kernel and co-snapshot storage. It does not
yet schedule region work or replicate entities. Next: owner-fenced asynchronous
installation, bounded native replication and cross-region handoff. Pickup/player
XP/recipe delivery remain subsequent prerequisites for earned-output admission.

Turn a durable pending XP obligation into bounded region-owned orb records exactly
once. Preserve the recipe-grant obligation until the player durably acknowledges
it. Live earned-output admission still waits for complete orb pickup/player XP and
recipe delivery; emitting packets alone cannot settle an award.

Acceptance:

- Native differential splitting, entity metadata and spawn/update/removal codecs
  for Java 26.3. Use persisted UUIDs with replaceable network IDs. Represent merged
  value/count explicitly; do not allocate one task/process per orb or XP point.
- Atomically install orb records and advance the matching pending obligation in
  the leased region snapshot/journal. Replay, capacity refusal, owner replacement
  and interrupted writes must preserve `pending XP + materialized XP` exactly.
  Zero-XP awards still retain recipe delivery. No unacknowledged obligation removal.
- Bound record count/bytes, pure worker work and replication batches. Cross-region
  spawn poses require fenced ownership handoff before effects are exposed. ETS
  observations cannot authorize transfers or pickup.
- Actual client: dedicated fresh fixture shows native orb types/icons/positions;
  cold owner/restart preserves records and no duplicate materialization. Keep
  pickup explicitly inactive until its player/durability prerequisites are complete.

## Materialization kernel

`CookingOrbs.materialize/3` proposes a whole `Containers` successor for one pending
award. It preserves the immutable award/recipe obligation, receipt, slots and entry
revisions. The owning region must validate its lease/current state and durably
commit before publishing effects; no live caller uses this API yet.

Split each recipe's decided XP separately using eleven denomination divisions,
then aggregate equal values into explicit counts. Persistent version-8 UUIDs derive
from award identity/value; runtime entity IDs are absent from storage. A marker and
its complete orb map share version-5 container bytes, with at most 256 markers,
2,816 records and 137,986 ledger bytes. Zero XP has an empty marked map and retains
recipe delivery. Encode/decode reject partial/altered/orphan records; the frozen
pre-pickup format cannot silently consume XP. No process/loop per XP unit.

Local-owner spawn positions only: boundary-crossing proposals return
`xp_orb_handoff_required` and retain pending XP. No cross-region effect is exposed;
the fenced handoff implementation is still open. Snapshot versions 1–4 retain exact
bytes when the new ledger is empty. Existing joint mining/container recovery embeds
version 5 without another journal or side file.

Native `ExperienceOrb.getExperienceValue/getIcon`, `DATA_VALUE` and generic entity
codecs are observed by original `ExperienceOrbOracle`. Metadata uses accessor 8,
integer serializer 1; Java 26.3 spawns XP through generic `add_entity`. Bounded spawn,
value metadata, motion, linear position and removal encoders are available but unused
for XP gameplay. Reference inspection stays in `.local/experience-orb.javap`.
