# VMC-021 — Anvil chunk/entity/region storage

Status: Awaiting client
Milestone: M2 real worlds
Depends on: [VMC-020](VMC-020.md) (NBT codec, world schemas, golden world oracle).

ValiMC worlds are flat terrain plus a sparse map of edited cells, persisted in
each region's log. Chunk packets carry one biome (plains) and full sky light.
Nothing reads or writes vanilla's Anvil region files, so no existing world can
be played, and a world that differs from flat terrain everywhere could not even
be stored efficiently.

Scope: import vanilla 26.3 worlds (blocks, biomes, block entities and entities of
every full chunk) into ValiMC's region storage and play them, and export them
back to Anvil files vanilla loads. What ValiMC does not model yet is preserved
for export rather than dropped.

Acceptance (parent):

- Region files are read with bounded, malformed-input-safe parsing: negative
  region coordinates, empty and corrupt header slots, sector ranges past the end,
  every compression vanilla writes (zlib, gzip, none, LZ4 block streams) and
  external `.mcc` chunks.
- For every full chunk of a golden vanilla world, every block state and biome
  ValiMC imports equals vanilla's (`getBlockState`/`getNoiseBiome`, dumped by an
  oracle). Non-full chunks are skipped and counted.
- Imported chunks persist in the region log as compact section images; edits on
  top of them survive restarts; untouched flat regions are unchanged.
- An imported world is playable with the actual client: terrain and biome
  colours match, blocks can be mined and placed, and a restart keeps the edits.
- Import throughput is benchmarked on the golden world.

Reference: pinned `RegionFile` (8 KiB header of 1,024 offset/sector entries and
timestamps; payload = length, compression byte, data; bit 128 = external
`c.X.Z.mcc`), `RegionFileVersion` (1 gzip, 2 zlib, 3 none, 4 LZ4),
`SerializableChunkData` (sections with `block_states`/`biomes` palette containers,
`Status`, `DataVersion`), `PalettedContainer` storage rules.

## VMC-021a — region file reader (October 20, 2026)

- `Valimc.Anvil.RegionFile` reads region files as the pinned `RegionFile` does.
  - Header slots are dropped when their sector overlaps the header, they have no
    sectors, or they start past the file end; a short header reads as empty.
  - Within a chunk, a short header, length 0, a negative or oversized length, or
    an unknown compression id reads as a missing chunk (vanilla logs and treats it
    as absent).
  - Id 127 (custom) is an error, since vanilla registers it but cannot read it.
  - An external chunk (+128) is read from `c.X.Z.mcc` beside the region file,
    even when an internal payload is also present.
- LZ4 block streams (lz4-java framing, xxHash32 checksums) decode in
  `valimc_core::lz4` through `Valimc.NBT.decompress(bytes, :lz4, max)`. Inputs
  over 256 KiB run on a dirty scheduler; output is bounded.
- Oracle stage `region_files` (`RegionOracle`, `check_region.exs`):
  - It runs the pinned server twice: a deflate world, and an LZ4 world with 48
    markers holding about 1.9 MB of random text in one chunk, which vanilla
    stores externally.
  - It derives 15 damaged copies of the fullest region file: short header,
    header only, a cut mid-chunk, overlapping, empty, past-end and at-end sectors,
    lengths 0/negative/too long, compressions 9 and 127, a missing and a present
    external file, and corrupt zlib.
  - Vanilla's `RegionFile` reads every slot of all 29 files: 4,001 chunks, 2 read
    errors, the rest missing. ValiMC matches slot for slot (canonical digests,
    errors and missing slots).
- Tests: `test/region_file_test.exs` (compressions, external chunks, header and
  chunk-header damage, a never-raises property, LZ4 with an independent Elixir
  xxHash32); `cargo test` for `valimc_core::lz4` (reference xxHash32 vectors,
  overlapping matches, corrupt and truncated streams).

## VMC-021b — chunk NBT to sections (October 20, 2026)

- `Valimc.Anvil.Chunk.column/2` turns a 26.3 chunk root into 24 section specs:
  - It accepts only full chunks at data version 5023; other statuses are skipped.
  - Block palettes map to state ids, cached across chunks. 26.3 writes an entry
    as a bare name (the default state) or `{id, properties}`, and a mixed palette
    wraps names as `{"": name}`.
  - Biome palettes map to registry ids.
  - Packing follows vanilla's storage rule: `max(4, ⌈log2 n⌉)` bits for blocks,
    `⌈log2 n⌉` for biomes, no data for one entry, never spanning longs.
  - A missing section is air in plains; light-only sections outside the world are
    ignored.
- Section storage (`valimc_core::section`):
  - `Storage::from_palette` and `Biomes::from_palette` unpack and validate the
    data length and indices.
  - Columns carry optional per-section biomes. `ColumnStore::put_column` and
    `dump_column` back `Blocks.put_column/3` and `Blocks.dump_column/2`.
  - Compaction keeps imported columns.
- Chunk packets encode per-section biomes: a single value, a 1–3-bit palette, or
  global ids at `Data.global_biome_bits/0` (7 bits for 67 biomes). Flat chunks
  still send uniform plains.
- Oracle stage `chunk_sections` (`ChunkOracle`, `check_chunk_sections.exs`):
  - The pinned server force-loads 16×16 chunks around spawn.
  - Vanilla's `SerializableChunkData.parse` loads each of the 1,764 overworld
    chunks; 400 are full, 1,364 have other statuses.
  - For every section of every full chunk, ValiMC's imported states (4,096 ids)
    and biomes (64 names) hash to vanilla's.
  - Vanilla's network `LevelChunkSection.read` decodes ValiMC's encoded chunk
    sections to the same blocks and biomes.
- Tests: `test/anvil_chunk_test.exs`, plus `cargo test` for packed palettes and
  biome encoding.

## VMC-021c — column images in the region log (October 20, 2026)

- `Column::to_image`/`from_image` (`valimc_core::column`): a versioned, compact
  image. Per section it holds a single state or a first-appearance palette with
  indices packed at `max(1, ⌈log2 n⌉)` bits, then the same for biomes. Decoding
  validates everything, and any other bytes are refused.
- Region logs gain a `columns` part (`chunk => image`), merged by chunk.
  - Owners load flat terrain, then the images, then the cell edits
    (`Blocks.new/3`, `Store.load_columns/1`).
  - `Store.import_columns/3` writes a new region's log offline (refused if the
    region already exists).
- Fixed in passing: the store dropped any cell equal to flat terrain, since flat
  was the base everywhere. In an imported chunk the base is the image, so such
  cells are now kept. `test/imported_region_test.exs` imports a cave, fills one
  cell with the stone flat terrain has there, restarts, and the stone stays; it
  fails with the old rule.

## VMC-021d — import tool and world spawn (October 20, 2026)

- `Valimc.Anvil.Import.run/2` imports into a new or empty directory with the
  server stopped. There are two entry points: `mix valimc.import SRC DST`, and
  `bin/valimc eval 'Valimc.Anvil.Import.cli(["SRC", "DST"])'` for releases.
  - Overworld region files convert in parallel, one task each.
  - A new NIF, `column_image_of`, turns each full chunk straight into a column
    image.
  - Images are grouped by ValiMC region and written with
    `Store.import_columns/3`.
  - The report counts imported chunks, skipped statuses and errors.
- `Valimc.World.Spawn`: the world's `world.json` holds the spawn block and yaw,
  written by the import from `level.dat` (`Data.spawn.pos`/`yaw`). New players,
  respawns, `/spawn` and the spawn packet use it; a generated flat world keeps
  (0, 64, 0).
- `chunk_sections` now also runs the importer on the oracle's world and reloads
  every written region log (`Store.durable(..., :columns)` into `Blocks.new/3`).
  All 400 full chunks reload to vanilla's per-section digests.
- Import benchmark (`bench/anvil_import.exs`, the oracle's world: 4 region files,
  400 full chunks; 10 schedulers):
  - Median of five whole imports: 294 ms (1,361 chunks/s), including 16 durable
    region-log checkpoints.
  - Per full chunk in one process: read and inflate 41 µs, decode 74 µs,
    palette conversion 77 µs, column image 60 µs.
  - The image was 430 µs while every section's palette was rebuilt per cell;
    indexed sections now pack their own palette and indices.
- Known limits for play: light is still full sky light (VMC-022), and block
  entities and entities are not imported (VMC-021e), so imported chests, signs
  and the like are missing their contents and render incompletely. Chunks
  outside the imported full area show flat terrain.

Client run (October 20, 2026; frozen `0abb3d3`; `.local/client-tests/VMC-021/`).
The vanilla world (seed 20261020, full chunks −10..9 on both axes, so x/z
−160..159) was imported with `mix valimc.import`. All scenarios PASS:

- Join: the player spawns at (0.5, 78, 0.5) on the grass block at (0, 77, 0) in
  savanna, on real terrain.
- Spot checks: (20, 74, 20), (100, 69, 50), (60, 79, −60), (−100, 75, −100) and
  (−40, 68, 30) show vanilla's block (F3 targeted block state) and biome. Grass is
  bright green in plains and yellow-olive in savanna.
- Terrain: hills, acacia and oak trees, a river, a lava lake, a savanna village
  and a pillager outpost, with no holes or stray blocks. The imported area ends in
  a sheer wall above ValiMC's flat terrain (expected).
- Edits: grass, dirt and an acacia log were mined, and stone and smooth stone
  placed. After a server restart and a fresh client, all of them persist, and the
  neighbouring imported blocks are unchanged.
- Server logs are free of errors and warnings.

Found in play, not specific to imports: breaking a block leaves a plant standing
on it (short grass floated above a mined grass block after reconnecting). ValiMC
has no vanilla support checks (`canSurvive` on neighbour updates) yet. Flat worlds
never showed it; imported terrain does everywhere. It belongs with neighbour
updates ([backlog](../backlog.md) VMC-029).

## VMC-021e1 — block entities (October 20, 2026)

- `Valimc.Anvil.BlockEntity.convert/2` reads a chunk's `block_entities` as
  vanilla's `LevelChunk` loads them.
  - Positions follow `BlockEntity.getPosFromTag`: missing coordinates read 0, and
    one filed in another chunk moves to the same offset in this chunk.
  - A compound whose `id` is not the type its block creates is dropped.
- Single chests and furnaces, smokers and blast furnaces become owned
  `Containers` entries when their compound holds only what ValiMC models.
  - That means `Items` (plus the furnace's times, speed and `RecipesUsed`).
    Vanilla writes `components` on every block entity, so an empty one counts as
    nothing.
  - `ItemData.stack/1` is the inverse of `ItemData.tag/1`: data-format item tags
    to `ItemStack`, reporting components ValiMC cannot hold yet. Fixed in
    passing: `tag/1` dropped a potion effect's `hidden_effect` chain.
- Everything else is preserved as its compound (`Valimc.World.BlockEntities`,
  region log part `block_entities`).
  - Chests and furnaces with a name, lock, unrolled loot table or unsupported
    items stay locked: they cannot open, and since their compound holds data,
    their block cannot be replaced.
  - Chunk packets carry each preserved entry's update tag. `update_tag/2`
    derives it from the compound following each type's `getUpdateTag` override:
    nothing, `saveCustomOnly`, `saveWithoutMetadata` (banners), the spawner
    without `SpawnPotentials`, or the campfire, shelf, brushable, trial spawner
    and vault fields.
  - A change that would replace a preserved entry holding data with another type
    is refused (`:unsupported_block_entity`).
  - So is a use of its block when the block overrides `useItemOn` or
    `useWithoutItem`, unless it is a secondary use with an item (that places, as
    in vanilla).
  - Entries are live only while their block still creates their type; readers
    check that instead of the owner rewriting the set.
- Owned furnaces now appear in chunk packets too (vanilla sends every block
  entity; theirs have empty update tags).
- `block_entities.json` (`BlockEntityOracle`) adds each run's type, the type
  registry (49 types; beds have none in 26.3) and the 132 interactive blocks.
- The importer keeps the rest of each chunk (structures, pending ticks, post
  processing and the like) as `chunk_extras` for export. Its report counts
  owned, preserved, locked and dropped block entities.
- Oracle stage `anvil_content` (`AnvilContentOracle`, `check_anvil_content.exs`):
  - The pinned server writes one block of each of the 48 placeable types plus
    richer fixtures: enchanted, named, lore, potion and book items, a furnace mid
    smelt, named and loot-table chests, signs, banners, a campfire, spawner, pot,
    skull, lectern, shelf, brushable sand, a double chest, vault and trial
    spawner.
  - All 74 block entities import as vanilla loads them: 9 owned containers whose
    every slot equals vanilla's loaded stack (decoded from vanilla's network
    encoding), 4 locked and 61 preserved compounds equal to vanilla's.
  - Vanilla decodes ValiMC's chunk packets for the 8 chunks to exactly its own
    block entity list: positions, types and update tags.
- Tests: `test/anvil_block_entity_test.exs` (item tags, conversion rules, update
  tags, preserved entries) and `test/imported_block_entities_test.exs` (an
  imported region renders a sign's text, refuses to replace or use it, and opens
  an imported chest with its contents).

## VMC-021e2 — entities (October 20, 2026)

- The importer reads the overworld `entities/` region files (chunk `Position`
  and `Entities`, schema-checked).
- `Valimc.Anvil.Entity.convert/1` turns a dropped item into an item record of
  the entity model, read as vanilla's `Entity.load` and
  `ItemEntity.readAdditionalSaveData` read it.
  - A motion component beyond ±10 is zero.
  - `Age` and `PickupDelay` are shorts. An age past 6,000 is 6,000 (it despawns).
    A negative delay never counts down, so it becomes the infinite 32,767.
  - The UUID, position, on-ground and no-gravity flags are kept.
- An item record belongs to the region its position falls in. At most 256 per
  region become records (the owner's bound); a repeated UUID is skipped, as
  vanilla's entity lookup skips it; items past the bound are preserved.
- Every other entity is preserved as its compound, per stored chunk, in the
  region log part `entities` for export. That covers mobs, items with an owner
  or riders, and items with components ValiMC cannot hold. (XP orbs were
  preserved too until VMC-021e4.)
  Item health and thrower are not modelled and are lost on export.
- The `anvil_content` stage now also summons items (supported and not), XP orbs,
  an armour stand and a villager; the generated chunks add chickens and pigs.
  - All 4 supported dropped items become records with vanilla's UUID, position
    and loaded stack.
  - The other 15 entities are preserved with exactly vanilla's stored compounds.
- Tests: `test/anvil_entity_test.exs` (vanilla's load rules, what stays
  preserved, export round trip).

## VMC-021e3 — Anvil export (October 20, 2026)

- `Valimc.Anvil.Export.run/2` writes a ValiMC world (server stopped) into a new
  or empty directory: `mix valimc.export VALIMC VANILLA`, or
  `bin/valimc eval 'Valimc.Anvil.Export.cli([...])'` in a release.
- One bounded task per vanilla region (each holds whole ValiMC regions).
- Every chunk beyond flat terrain is exported: imported columns, edits,
  containers, items and preserved entities. `Chunk.to_nbt/5` writes it as a full
  chunk.
  - Sections use 26.3's palettes: default states as names, others as
    `{id, properties}`.
  - Block entities: owned chests and furnaces from their contents
    (`BlockEntity.container_tag/3`), plus the preserved compounds whose block
    still creates their type.
  - The import's `chunk_extras` (structures, pending ticks, post processing) are
    written back.
  - Heightmaps and light are left to vanilla (`isLightOn` 0), since edits make
    imported light stale.
  - Vanilla generates every other chunk itself.
- Items become `minecraft:item` compounds (`Entity.item_tag/1`). Preserved
  entities return unchanged to their stored chunk.
- The import now keeps every vanilla file except chunk storage under `vanilla/`.
  In 26.3 that is `level.dat` plus world and dimension data: world generation
  settings, game rules, weather, clocks, world border and the like. A server
  cannot start without the generation settings. Export writes them back, with
  `level.dat` carrying the world's current spawn.
- `RegionWriter` lays chunks out as vanilla's `RegionFile` reads them.
  - Compression is zlib. Chunks are padded to 4 KiB sectors from sector 2, and
    the header holds offsets, counts and write times.
  - A chunk over 255 sectors goes to `c.X.Z.mcc` with compression +128.
  - Files are written crash-safely: temporary name, sync, rename, directory
    sync. External chunks are written before the region file that points at
    them.
- Block palettes are packed in Rust (`valimc_core::section::pack_vanilla`, NIF
  `pack_paletted/2`); the Elixir reference `Chunk.pack_reference/2` checks it.
- Oracle stage `anvil_content`, step `export`:
  - Before any server runs, the export must equal the original as vanilla loads
    both: every section's blocks and biomes, and every block entity through
    `loadStatic`/`saveWithFullMetadata`. Preserved entities must be unchanged;
    items must keep their UUID, position, motion, age, delay and stack.
  - Then the pinned server runs on a copy of the export, and on a copy of the
    original reduced to what an import keeps (full chunks, no POI files). Both
    runs are frozen (`tick freeze`), force-load every exported chunk and save.
  - Any logged error fails the stage. Both saves must hold the same chunks and
    the same entities in exported chunks.
  - Loading applies vanilla's pending post processing to both alike.
  - Generating a missing neighbour can place features into a bordering chunk,
    and parallel generation does not always do so identically. Only chunks
    whose eight neighbours were exported too are compared after the runs.
    Generated neighbours also spawn their own animals, which are not compared.
  - Result: 64 full chunks with 74 block entities and 19 entities match before
    the runs, and 36 interior chunks after them.
- Benchmark (`bench/anvil_export.exs`, the 400-chunk `chunk_sections` world, 10
  schedulers). Another session's suites kept the load average near 45, so read
  these relative to each other.
  - Median of five exports: 393 ms.
  - Per chunk in one process: column dump 88 µs, chunk NBT 1,067 µs, NBT write
    163 µs, zlib 826 µs.
  - Block palette packing for 24 sections: Rust 963 µs, Elixir reference
    5,526 µs. In Elixir, chunk NBT took 4.1 ms per chunk and the export median
    was 675 ms at a lower load.
- Tests: `test/anvil_export_test.exs`.
  - Region files read back slot for slot, including an external chunk and
    header times.
  - A chunk's NBT imports back to the same column.
  - Native packing equals the reference.

## VMC-021e5 — stored light (October 20, 2026)

- Imported chunks saved with `isLightOn` keep their stored light
  (`Valimc.Anvil.Light`, region log part `light`, loaded by the owner).
  - Per light section (y −5..20), each `SkyLight`/`BlockLight` array is kept as
    absent, one repeated byte, or its 2,048 bytes.
  - Chunk packets send exactly the stored arrays with their masks.
- Vanilla stores sky light only around the surface and block light only where
  it is not zero. The client derives the rest (a missing sky section takes the
  next stored one above or full sky; missing block light is zero), so imported
  caves, interiors and torches look as they do in vanilla. Chunks without
  stored light (flat terrain, chunks not lit when saved) keep full sky light.
- Limit until VMC-022: light is not recomputed when blocks change. The client
  relights what it sees change, but a later join sees the imported light (a
  torch placed in a cave does not light it for a newly joined player).
- Oracle: `AnvilContentOracle verify` decodes ValiMC's packets for the 8 fixture
  chunks with vanilla's codec. Masks and arrays equal the stored light of each.
- Cost (same benchmark run): a chunk frame averages 5,981 bytes with stored
  light against 5,459 full-bright after network compression. Encoding takes
  905 µs against 861 µs.
- Tests: `test/anvil_light_test.exs` (the full-bright packet is byte-identical
  to the previous one; masks and arrays; invalid light refused).

## VMC-021e4 — XP orbs (October 20, 2026)

VMC-067 made entity presentation generic (one view, publication and replication
for items and orbs), but durable state stayed kind-specific. Items have
standalone records. An orb exists only as a birth of a cooking award, the
furnace decision whose source, sequence and digest make pickup and transfers
idempotent. A vanilla orb has no award behind it, so this slice gives orb births
a second origin rather than inventing furnace awards.

- `PendingCookingAwards.put_imported/5`: an imported orb is an award record
  under the reserved nil-UUID source, sequence n, holding the orb's UUID, value
  and count instead of recipe rows.
  - On disk it is a record with zero recipe rows followed by the orb, so older
    data reads unchanged.
  - The import source's receipt covers the last imported sequence, as every
    award source must.
- `CookingOrbs.records/2` turns an imported award into its single birth with
  vanilla's UUID. `CookingOrbs.import_orbs/3` adds orbs to a new region's
  containers as materialized births with bodies (position, motion, age,
  on-ground, no-gravity); `Containers.encode/2` validates the result.
- From there the existing machinery applies unchanged: publication, pickup
  consumption, ageing and despawn at 6,000 ticks.
- `Entity.convert/1` reads an orb as vanilla's `ExperienceOrb` stores it.
  - `Value` is a short (1..32,767) and `Count` an int (default 1).
  - The motion rule is the entity one. An age at 6,000 or above becomes 5,999
    (vanilla discards it on the next tick).
- The importer takes orbs in stored order while the region's 256 award slots
  last, skips a repeated UUID, and preserves the rest.
- Export writes every orb a region holds, imported or from cooking, as an
  `experience_orb` with its remaining count at its body. `Entity.item_tag/1` and
  `orb_tag/4` now write the fields vanilla writes (`fall_distance`, `Fire` 0,
  `NoGravity` only when set).
- The `anvil_content` stage checks all 4 fixture orbs: births with vanilla's
  UUID, value and count, and bodies at vanilla's positions. The export oracle
  compares orbs' UUID, position, motion, age, value and count.
- Tests: `test/anvil_entity_test.exs` (orb reading and export round trip) and
  `test/cooking_orb_runtime_test.exs` (imported orbs load from the region log,
  publish at their bodies with their values and counts, and all expire 6,000
  ticks later).
