# VMC-021 — Anvil chunk/entity/region storage

Status: In progress
Milestone: M2 real worlds
Depends on: [VMC-020](VMC-020.md) (NBT codec, world schemas, golden world oracle).

ValiMC worlds are flat terrain plus a sparse map of edited cells, persisted in
each region's log. Chunk packets carry one biome (plains) and full sky light.
Nothing reads or writes vanilla's Anvil region files, so no existing world can
be played, and a world that differs from flat terrain everywhere could not even
be stored efficiently.

Scope: import vanilla 26.3 worlds (blocks and biomes of every full chunk) into
ValiMC's region storage and play them; keep what is not yet modelled (block
entities, entities, light, POI) for later slices. Export to Anvil comes after.

Subtickets:

| VMC-021b | Chunk NBT to section storage: block states and biomes per section | In progress |

| VMC-021d | Import tool, spawn from `level.dat`, biomes in chunk packets; client run | Planned |

Acceptance (parent):

- Region files are read with bounded, malformed-input-safe parsing: negative
  region coordinates, empty and corrupt header slots, sector ranges past the end,
  every compression vanilla writes (zlib, gzip, none, LZ4 block streams) and
  external `.mcc` chunks.
- For every full chunk of a golden vanilla world, every block state and biome
  ValiMC imports equals vanilla's (`getBlockState`/`getNoiseBiome`, dumped by an
  oracle). Non-full chunks are skipped and counted.
- Imported chunks persist in the region log as compact section images; edits on
  top of them survive restarts; untouched flat regions are unchanged.
- An imported world is playable with the actual client: terrain and biome
  colours match, blocks can be mined and placed, and a restart keeps the edits.
- Import throughput is benchmarked on the golden world.

Reference: pinned `RegionFile` (8 KiB header of 1,024 offset/sector entries and
timestamps; payload = length, compression byte, data; bit 128 = external
`c.X.Z.mcc`), `RegionFileVersion` (1 gzip, 2 zlib, 3 none, 4 LZ4),
`SerializableChunkData` (sections with `block_states`/`biomes` palette containers,
`Status`, `DataVersion`), `PalettedContainer` storage rules.

## VMC-021a — region file reader (October 20, 2026)

- `Valimc.Anvil.RegionFile` reads region files as the pinned `RegionFile` does.
  - Header slots are dropped when their sector overlaps the header, they have no
    sectors, or they start past the file end; a short header reads as empty.
  - Within a chunk, a short header, length 0, a negative or oversized length, or
    an unknown compression id reads as a missing chunk (vanilla logs and treats it
    as absent).
  - Id 127 (custom) is an error, since vanilla registers it but cannot read it.
  - An external chunk (+128) is read from `c.X.Z.mcc` beside the region file,
    even when an internal payload is also present.
- LZ4 block streams (lz4-java framing, xxHash32 checksums) decode in
  `valimc_core::lz4` through `Valimc.NBT.decompress(bytes, :lz4, max)`. Inputs
  over 256 KiB run on a dirty scheduler; output is bounded.
- Oracle stage `region_files` (`RegionOracle`, `check_region.exs`):
  - It runs the pinned server twice: a deflate world, and an LZ4 world with 48
    markers holding about 1.9 MB of random text in one chunk, which vanilla
    stores externally.
  - It derives 15 damaged copies of the fullest region file: short header,
    header only, a cut mid-chunk, overlapping, empty, past-end and at-end sectors,
    lengths 0/negative/too long, compressions 9 and 127, a missing and a present
    external file, and corrupt zlib.
  - Vanilla's `RegionFile` reads every slot of all 29 files: 4,001 chunks, 2 read
    errors, the rest missing. ValiMC matches slot for slot (canonical digests,
    errors and missing slots).
- Tests: `test/region_file_test.exs` (compressions, external chunks, header and
  chunk-header damage, a never-raises property, LZ4 with an independent Elixir
  xxHash32); `cargo test` for `valimc_core::lz4` (reference xxHash32 vectors,
  overlapping matches, corrupt and truncated streams).
