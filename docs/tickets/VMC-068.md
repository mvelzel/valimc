# VMC-068 — Unified block registry, block behaviours and version pins

Status: In progress
Milestone: M1 foundations
Depends on: none (parallel to the world tickets).

Before this slice the pinned version was spelled out in about 35 modules: each
fact module compared its JSON stamp against literal `"26.3"`, `5023` and the server
jar SHA-1, persistence records embedded `5023::32`, and five import scripts
repeated the same asserts. The block state count `35_723` was hard-coded in 33
places. No module knew which block a state belongs to except `MiningTools`
(a private 2-byte table), and `blocks.json` duplicated eight default states and
an item→block map. Block-specific behaviour was spread over the callers: about 25
call sites wrote `ChestAccess.single?(b) or CookingBlocks.kind(b) != nil` or
switched on item ids for chest, furnace, slab and pillar placement.

Fact families today (all generated from the pinned jar unless noted):

| Family | Source | Module |
|---|---|---|
| Version | jar `version.json`, Mojang manifest | literals (this ticket: `Valimc.Version`) |
| Packets, registries, tags | data reports, `ProtocolMetadata` | `Valimc.Protocol.Data` |
| Items and components | `ItemMetadata` | `Valimc.Protocol.ItemTypes` |
| Block states (count, owner block, defaults) | data reports (partial) | `Data`, `MiningTools` (this ticket: `Valimc.Registry.Blocks`) |
| Per-state physics/mining/placement facts | one `*Metadata`/`*Oracle` each | `Valimc.Physics.*` (dense per-state byte tables) |
| Chest, furnace-family states | `ChestAccessOracle`, `import_cooking_blocks.py` | `ChestAccess`, `CookingBlocks` |

The per-state physics tables stay separate: each is one concept with its own
oracle and dense index, so merging them would only move bytes.

After this slice:

- `Valimc.Version` reads `priv/version.json`, generated by `VersionMetadata` from
  the running jar (`SharedConstants`) and the jar's SHA-1. Every module that loads
  stamped facts checks them through `Valimc.Version.stamped?/2` (six modules that
  loaded stamped files unchecked now check them too). `Valimc.version/0` and
  `protocol_version/0` delegate to it. The Python tools read the same file through
  `scripts/pinned.py`; `prepare_vanilla.py` refuses a manifest or jar that differs.
- `Valimc.Registry.Blocks` is generated by `BlockRegistryMetadata` into
  `priv/registry/blocks.json`: every block in registry order with its state run,
  default state, property definitions and vanilla block class. It owns
  `state_count/0`, `block_id/1`, `default_state/1`, `properties/1` and
  `class/1`. `Data.block/1`, `Data.item_block/1` (derived: an item places the
  default state of the same-named block) and `MiningTools.block_id/1` delegate to
  it. `priv/protocol/blocks.json` is gone (the player entity type comes from
  `EntityTypes`), `mining_tools.json` lost its private state→block table, and the
  hard-coded state counts read `Valimc.Registry.Blocks.state_count/0`.
- `Valimc.Block` dispatches per state to a `Valimc.Block.Behaviour` module chosen
  by its generated class (`ChestBlock` → `Chest`, the furnace classes →
  `Cooking`, slab classes → `Slab`, `RotatedPillarBlock` family → `Pillar`,
  everything else → `Default`). Callbacks: `block_entity/1`, `placement/5`,
  `harvest_drops/1` and `after_removal/1`. Callers ask `Valimc.Block` instead of
  testing chest and furnace identity themselves.

Scope limits: Java oracles still stamp their own output literally (the Elixir
stamp check rejects a mismatch at compile time). Persistence record headers keep
their literal `5023::32` tag: it names the on-disk format of existing logs, and a
version bump must not make old records undecodable. The MOTD and the data-pack
rejection text keep their literal version. No new block behaviour is added;
`connection.ex` and `region_data.ex` get call-site renames only (VMC-064 and
VMC-069 own those files).

Acceptance:

- Changing a pinned value in `priv/version.json` fails compilation of every fact
  module whose stamp no longer matches; `check_vanilla.py --only version`
  regenerates the file byte-equal.
- `BlockRegistryMetadata` regenerates `priv/registry/blocks.json` byte-equal
  (`check_vanilla.py --only block_registry`), asserting contiguous runs and the
  mixed-radix property order of every state.
- Every item the placement tables support dispatches to the same branch as before
  (compile-time cross-check in `Valimc.Physics.Placement`).
- Gameplay is byte-identical: the existing suites and the placement, mining,
  block-entity, chest, cooking and fluid oracle stages pass unchanged.
- `Valimc.Block.block_entity/1` is no slower than the two lookups it replaces
  (`bench/block_behaviour.exs`).

Plan:

3. Behaviour layer and call-site migration; benchmark.
