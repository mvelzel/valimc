# VMC-014b2 — Scaffolding collision contexts

Status: Done
Note: Done — geometry and actual client contacts verified. October 14, 2026. Depends on completed VMC-014a/VMC-014b1.

Resolve all 32 scaffolding states with a pure, explicit collision context. Native
rules distinguish empty queries, placement, descending entities and feet height;
holding scaffolding affects its outline, not its collision shape.

Acceptance:

- Extract native stable/unstable-bottom geometry and state distance/bottom facts.
- Use bounded immutable contexts. Match native `isAbove` epsilon and strict
  comparison, empty-context defaults and placement's empty collision result.
- Compare every state/context branch and height boundary against actual Mojang
  methods. Unknown states and other unresolved dynamic families stay explicit.
- Pass format, full tests/native oracle, release, exact diff and public-tree audit.
- Actual 26.3/CUA: render scaffolding fixtures, land on the platform and descend
  with Shift; compare contact/empty geometry, verify commands and reconnect.
  Fresh client logs are required; a locked GUI gate must not halt the backlog.

Reference: pinned 26.3 SHA-1 `33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`,
`ScaffoldingBlock.getCollisionShape`, `EntityCollisionContext.isAbove` and its empty
subclass. Private bytecode: `research/disassembly/VMC014b2-contexts.txt`.

Server movement/climbing enforcement and scaffolding support/placement updates
remain separate work. Powder snow also needs fall distance, falling-block identity,
walkable entity tags and leather boots; handle it in VMC-014b3.

retain their voxel boundaries. Position-only calls still require a scaffolding
context; 115 states in other dynamic families remain unresolved.
