# VMC-019b1 — Atomic region item inbox and durable retry receipts

Status: Done — destination retry foundation validated. Updated: October 14, 2026.
Depends on VMC-019a. First slice of VMC-019b; gameplay drops remain incomplete.

## Scope and acceptance

Before: an uncertain create reply cannot safely be retried, particularly after
the original entity was removed. After: a region applies a bounded item batch and
its source receipt in the same writer-acknowledged file replacement. Retrying the
same accepted request never creates another item, including after removal/restart.

- A trusted internal request contains a source player UUID, positive unsigned
  64-bit sequence and 1–5 stable-UUID stationary item records in this region.
  Exact supported stack patches and positions contribute to a canonical digest.
  This API is not exposed to client packets and does not consume inventory.
- Retain one sequence/digest high-water receipt per source per region, bounded at
  4096 sources. Equal sequence/equal digest acknowledges `already_applied` without
  I/O or item recreation. Equal sequence/different digest rejects a conflict;
  lower sequences reject as stale. Newer sequences replace that source's receipt.
  Duplicate live item UUIDs reject; invalid or over-budget batches are atomic.
- Source ordering is a contract, not implemented by this destination slice:
  a future leased player writer durably commits one outbox before sending it,
  pins destination/UUIDs/sequence, finishes recovery before admitting another
  transfer, and never reuses/wraps sequences. Stale source actors cannot recreate
  older batches. Coordinated backup restoration and eventual source retirement
  are separate work; exhausting the source cap must reject rather than evict a
  receipt. No unbounded per-transaction history or global gameplay coordinator.
- Item file version 2 stores both items and receipts atomically. Version 1 remains
  read-only compatible and gains an empty receipt map; no-receipt scene saves can
  retain version 1. Bound item payload, source count, total bytes and read size;
  reject corrupt/duplicate/invalid receipts without overwriting files.
- Existing one-pending-proposal gate, matching writer/token acknowledgment,
  five-second deadline, uncertainty fencing and recovery from the actual file
  apply to transfers. Item replacement/removal and block snapshots preserve
  receipts. No item/receipt publication before acknowledgment.
- Pure batch validation/digest/cached packet preparation runs in a supervised
  worker pool bounded by the online scheduler count. A region admits one job;
  saturation rejects without a queue, and captured immutable state is fenced by
  worker/token/monitor. Region block operations/ticks continue during planning.
- Tests cover exact/conflicting/stale retries, removal and owner replacement,
  source sequencing, stable UUID collision, multi-item atomicity/count/byte limits,
  source cap, codec/migration/corruption, stalled writes and commit-before-reply
  failure recovery. Run format/full tests/release/full Mojang oracle/audit.

Actual Minecraft 26.3 via CUA: apply an internal fixture transfer at the camera,
observe one item, retry and observe no additional item; remove it, retry and
observe absence; restart/rejoin without reseeding and retry again, confirming
absence, the exact persistent receipt and empty inventory. Use a temporary world
and record that fixture creation is not an inventory-originated gameplay drop.

## References and design

Pinned Mojang 26.3 jar `33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`:
`ItemEntity.playerTouch` mutates inventory and removes/depletes the entity; current
private `VMC018-ItemEntity.txt` demonstrates why entity presence cannot serve as a
retry receipt. Vanilla has no BEAM cross-owner inbox protocol; this is original
recovery infrastructure, not a claim that vanilla uses this file/ledger design.
SteelMC `f6fb4e49778c`, `player_inventory/player_handlers.rs` separates selected
stack removal from spawning and pickup delay; Pumpkin `b0c48b2d7688`,
`entity/player.rs` separates held-stack decrement and world spawn and has explicit
item merging omissions. These paths supply boundaries, not crash-atomicity proof.
Dragonfly `1793369709ce`, `server/world/tx.go` restricts mutation to its owner
transaction. ValiMC uses owner-local pure planning plus its existing disk writer.
No reference source is copied or published.

## Verification

October 14, 2026, Elixir 1.20.4 / OTP 29.1.1, Minecraft Java 26.3:

- Format and all 136 ExUnit tests pass, seed 27545. Fourteen new regressions cover
  canonical batches/order, exact/conflicting/stale retries, monotonic receipts,
  stable UUID collision, atomic partial count/byte failure, invalid requests,
  bounded source admission/progression, file versions/receipts/migration and
  corruption, removal/recovery, scene/block-save preservation, stalled storage,
  physical commit with withheld reply, writer loss, CPU pool saturation, controlled
  blocked-job loss/stale replies and planning deadline/owner/job termination.
- Production release and full Mojang codec/TCP oracle pass (01:14:05). Entity
  packets/replication are unchanged; the oracle retains complete existing chunk,
  registry, inventory, player, command and preview interaction coverage.
- Item version 2 admits 524,288 bytes of item payload plus 4096 fixed 56-byte
  source receipts, 25-byte header and 32-byte checksum: at most 753,721 bytes.
  Version 1 (23-byte header) loads without receipts; no-receipt writes keep it.
  No receipt eviction is implemented. Nil storage is explicitly ephemeral.
- Pure preparation runs in `ItemWorkers`, with scheduler-count maximum children
  and no queued region submissions. Planning and storage share the original
  five-second deadline. The existing writer commits records/receipts atomically
  before publication/reply; worker loss before disk submission clears admission.
  Tests directly control stalled writer/job boundaries, not elapsed screenshots.
- Actual release restarted at 01:14:49 in the existing temporary world. Window
  observation initially returned `cgWindowNotFound`; rebinding the dedicated app
  and its exposed Raise action restored observation. CUA Tab/Return joined the
  observed localhost entry. The unchanged isolated SDL adapter remains loaded;
  these checks require only keyboard navigation and observation.
- An internal inbox fixture used a separate random source UUID/sequence 1 and
  stable item UUID, stone 7 with glint/custom NBT half a block along the camera.
  Minecraft visibly rendered the stack; owner/file comparisons matched its exact
  record and canonical receipt (185-byte version 2 file). Exact retry returned
  `already_applied`, left one authoritative entity and byte-identical file, and
  the same stack remained visible. F3's reduced overlay supplied no independent
  entity count; it was hidden again. Counts come from owner/file assertions.
- Removal then exact retry kept zero items and one receipt in a 113-byte file;
  actual Minecraft visibly cleared the stack. A conflicting stack-8 request
  returned `transfer_conflict` and left zero views.
- Full release restart at 01:16:41, actual CUA rejoin (client log 01:17:03) and
  exact retry without reseeding kept the item absent. Receipt fields/file bytes
  remained exact, records/publication stayed empty, and inventory slots/cursor
  remained empty. A conflicting retry after recovery also left the observed world
  clear. No item fixture remains; its receipt is intentionally retained in the
  disposable test world to establish recovery, separate from real player history.
- Private log copy `.local/client-tests/VMC-019b1/latest.log` has zero Network
  Protocol Error, DecoderException, EncoderException, Duplicate entity or ERROR
  entries. Public-tree audit/self-checks and exact diff review pass.

This proves the destination inbox contract under its documented source-ordering
assumption. It does not yet prove an inventory-to-world transaction, pickup/drop
physics or power-loss durability. VMC-019b2 adds the durable leased player source
outbox/sequence and ordered checkpoint fencing. Session orchestration/actual drop
controls, safe receipt retirement, physics/merging/pickup/despawn and cross-region
handoff remain; VMC-019b and the full vanilla-server goal remain incomplete.
