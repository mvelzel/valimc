## Scope and acceptance

Before: the source API accepts only conserved inventory transfers, so a creative
drop cannot create an item without misrepresenting its source. After: a separate
leased-owner API journals one authorized new supported stack while retaining the
entire inventory. Normal transfer conservation remains mandatory. This ticket
does not accept creative drop packets or complete the creative controls milestone.

- Require the calling writer owner, current fence, loaded persistent source,
  no pending intent, and trusted live infinite-material permission. Permission
  is not a client flag, persisted privilege or property inferred from item data.
- Accept exactly one nonempty supported record, within existing component/count/
  position/byte limits. Preserve inventory slots/cursor/selection and exact patches.
  Advance the shared monotonic sequence and commit inventory/outbox together.
  Use existing receipt verification, fence rotation, retry delivery and clear.
  Do not add a generic conservation bypass, format change or global coordinator.
- Unauthorized/invalid/stale/foreign/disabled/pending requests create nothing.
  A write failure preserves old storage and fences the uncertain writer. A lost
  acknowledgment or writer replacement recovers the pinned creation intent.
  Already delivered/removed creation retries cannot mint another copy.
- Regression tests cover the pure conservation boundary, exact supported creation,
  authorization/record limits, writer admission/failure boundaries, receipt proof,
  lost reply/reopen and automatic login recovery. Format/full tests/release/oracle/
  public-tree audit and exact diff review pass before the local checkpoint.

## Reference conclusions and architecture

Pinned Mojang 26.3 server SHA-1 `33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`:
`ServerGamePacketListenerImpl.handleSetCreativeModeSlot` first checks live
`ServerPlayer.hasInfiniteMaterials` and item feature availability. Any negative
signed slot selects creation/drop; slots 1..45 select inventory writes. Legal
nonempty stacks respect their effective maximum. The drop branch checks then
increments `TickThrottler(20,1480)`, calls predicted creative drop, and does not
consume an inventory slot. Empty drops still charge the throttle but spawn no item.
`TickThrottler.tick` decays by one, and admission requires count strictly below
1480. Private bytecode inspections stay under ignored `research/disassembly/`.
Client `CreativeModeInventoryScreen.slotClicked` can send a drop followed by an
independent creative slot write. Connected integration must preserve both actions;
reusing the conserved-transfer mutation freeze blindly would reject that write.

SteelMC `f6fb4e49778c` `player_inventory/player_handlers.rs` separates negative
creation from slot writes and keeps its throttle in connection/session state;
its tests preserve throttling across respawn. Pumpkin `b0c48b2d7688`
`pumpkin-core/src/net/java/play/set_creative_slot.rs` also separates the branches,
with plugin cancellation and no throttle in this handler. Paper `a2d844f71e27`
listener patches add plugin events/cancellation; those are not vanilla rules.

Original Elixir plans expose an explicit creation operation, restricted to one
record and the trusted leased owner. The existing per-player writer persists the
intent; region receipt/outbox recovery does not care whether the record originated
from consumption or authorized creation. Recovery never evaluates permission
again or creates fresh UUIDs. Saved inventory continues to reset authority on
decode; normal session initialization supplies current permissions. Existing
stationary physics/pickup/age/stats, feature negotiation, power-loss qualification
and receipt-retirement gaps remain. Connected creative ordering/throttling is
VMC-019b3d2, not a claim from this source API.
