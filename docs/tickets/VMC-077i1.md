# VMC-077i1 — One player schema and codec

Status: Done
Milestone: foundations II (between M2 and M3)
Depends on: [VMC-077i](VMC-077i.md), [VMC-077f](VMC-077f.md) (checkpoints),
[VMC-077k](VMC-077k.md) (the living state).

Before: a player's durable state had no schema. `PlayerSnapshot` captured an
untyped map whose keys were optional, encoded it in a custom binary of 22
written versions (a base of eleven and wrappers for the table, fire, effects,
absorption, progression, dimensions and credits, each with base-version
guards), and the fields a save keeps were listed in four places that had
diverged: an XP pickup while a crafting table was open wrote a file nothing
could read (player-connection E1), and a save with a transfer pending lost the
absorption pool (E3).

Acceptance:

- `Valimc.Player.State` is the one schema: pose, dimension, inventory (slots,
  selection, cursor, the open table's grid), game mode, flight, the living
  state's saved fields, food, progression, fall distance, velocity, last death
  and its dimension, portal cooldown, seen credits, and the pending transfer
  (`transfer_sequence`, `outbox`) until VMC-077i3 deletes it.
- One codec: the player file is a checkpoint of keyed records
  (`Valimc.Storage.Checkpoint`), one per field and one per occupied inventory
  slot, with the player's uuid. Every field is validated before it is written
  and after it is read, by the rules that own it. Any other format, another
  player's file, a missing field or a changed byte is refused (D4); there are
  no versions to read.
- A save with a transfer pending keeps every durable field of the live player
  but the transfer-bound ones (`merge/2`); the player store stamps its own
  transfer sequence on a live capture. E1 and E3 cannot recur.

Deleted: `PlayerSnapshot` (788 lines) and the tests of its version wrappers.

Checks: `mix test.fast` and the full `mix test` (one run: every login and
connection test reads and writes player files), the changed vanilla stages
(`check_vanilla.py --changed`), the audit.
