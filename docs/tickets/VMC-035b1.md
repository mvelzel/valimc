# VMC-035b1 — Cross-owner item merging

Status: Done
Note: **Done for current untargeted item lifecycle**, October 16,2026. Final runtime `a2f7770af51ad660a295eae2bdaa2f88087bdecf`. Persistent exclusive targets remain in [VMC-035c1](VMC-035c1.md).

Acceptance: compatible items straddling an ownership boundary merge with native
range/stack/age/delay behavior. Define one bounded decision authority, durable
withdrawal/adoption and receipt recovery. Never mutate from published views or
move an entity into an owner that cannot own its physical position. Contention,
capacity, simultaneous handoffs, duplicate messages and either-owner crash conserve
UUIDs/counts. Measure the added work.

Client scenario: actual drops land on both sides of x128 within native merge
distance, converge automatically, then survive fresh reconnect and owner recovery.
Unlike components, excessive totals and out-of-range items stay separate.

Protocol: a donor owner durably escrows its item before the recipient
owner changes a stack. The recipient commits a typed applied/rejected receipt;
only authoritative proof lets the source clear escrow or restore its donor.
One source sequence/outgoing lane orders merges with existing owner handoffs.
Reserve destination receipt capacity and source return capacity before withdrawal;
never hold both owners waiting on each other or authorize from observations.
Native custom 99 can shrink a65 recipient to 64 and return 2 to a1 donor, so escrow
must support a nonempty donor after success, not just removal or rejection.
