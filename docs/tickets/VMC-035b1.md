# VMC-035b1 — Cross-owner item merging

Status: Open; same-owner merging is validated in VMC-035b.

Acceptance: compatible items straddling an ownership boundary merge with native
range/stack/age/delay behavior. Define one bounded decision authority, durable
withdrawal/adoption and receipt recovery. Never mutate from published views or
move an entity into an owner that cannot own its physical position. Contention,
capacity, simultaneous handoffs, duplicate messages and either-owner crash conserve
UUIDs/counts. Measure the added work.

Client scenario: actual drops land on both sides of x128 within native merge
distance, converge automatically, then survive fresh reconnect and owner recovery.
Unlike components, excessive totals and out-of-range items stay separate.

Protocol in progress: a donor owner durably escrows its item before the recipient
owner changes a stack. The recipient commits a typed applied/rejected receipt;
only authoritative proof lets the source clear escrow or restore its donor.
One source sequence/outgoing lane orders merges with existing owner handoffs.
Reserve destination receipt capacity and source return capacity before withdrawal;
never hold both owners waiting on each other or authorize from observations.
Native custom99 can shrink a65 recipient to64 and return2 to a1 donor, so escrow
must support a nonempty donor after success, not just removal or rejection.

`ItemMergeTransfer` currently provides a canonical≤131,404-byte proposal with exact
source/destination-owned records, generations, sequence and permit, native decision
direction/range and distinct terminal proof.12 affected checks pass(seed213441),
`.local/item-cross-merge-request-targeted.log`, including negative boundaries,
malformed/trailing/oversized bytes, native limits and the custom99 reverse flow.
Existing native pair/geometry oracles support the reused kernel.

Pure escrow/inbox checkpoint: typed ledger journals retain the original donor and
one cached return reservation. Existing births/replacements/motion cannot consume
its entity/byte capacity. Typed destination proof clears it or returns the donor
under a newer generation; both save/reload cuts preserve receipts. Regional
sequence0/digest0 reserves incoming source capacity without acknowledging a
transfer; existing handoffs share and advance it.71 affected checks pass
(seed313138), `.local/item-cross-merge-checkpoint-targeted-final.log`: ordinary/reverse
flow, stale/moved/expired contexts, competing donors and retry, full entity/large
component return budgets, codec recovery and legacy handoff/pickup regressions.
No API currently starts these journals. Live admission/inboxes/recovery/discovery,
fault probes, measurements and actual Minecraft remain open. Equal-count discovery
must select one deterministic donor to prevent opposing simultaneous withdrawals.
