# VMC-032a3 — Container request/receipt foundation

Status: Implementing; live chests remain disabled.

Acceptance: a bounded typed request binds the player inventory/cursor, operation,
container revision/content, source sequence and owner permit. Recompute the native
click plan rather than trusting client predictions. Region contents and applied/
rejected receipts share one atomic snapshot. Retries after writer/owner restart
recover the committed outcome exactly; competing stale views reject without item
loss, duplication or partial player changes. Reserve receipt capacity before grants.

Player ownership order: persist the original inventory plus one intent, block
conflicting item actions, deliver the request, then seal the deterministic player
result only after a matching durable applied receipt. Rejected receipts retain the
original inventory. Receipt lookup precedes expired permit checks for recovery.
One high-water mark per player per region bounds replay metadata; source sequences
may have gaps from other transfer kinds. No process per chest/global transaction owner.

First implement request/receipt kernels and storage; player-journal and live region
composition follow. Tests cover competing deposits/withdrawals, encoded restart,
lost acknowledgment/replay, conflicting digest, stale sequence, capacity and invalid
payloads. Native click correctness is VMC-032a2. Before live UI, require actual
multi-viewer transfer/close/reconnect/removal/recovery scenarios with a dedicated tester.
