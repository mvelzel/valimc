# VMC-034n2 — Durable pending cooking awards

Status: Implemented; actual-client storage/regression gate pending.
Depends on [award values](VMC-034n1.md); part of [earned output](VMC-034n.md).

Preserve a decided XP/recipe award alongside a container transaction before any
entity or player effect. Keep output withdrawal refused until the full delivery
path is implemented; storage acceptance alone must not enable it.

Direction: reuse the region's leased writer and atomic container snapshot/joint
block-item-container journal. Region ownership covers pending awards; no process
per award and no independent file whose acknowledgement can diverge from cleared
credit. Inspect `Containers`, `ContainerTransfers`, `MiningRecord`, `Store` and
`PlayerContainerIntent/Transfers` selectively.

Implementation boundary: an internal, unused transfer planner stages pending
awards in a version-4 container snapshot. The live connection/region path continues
to use the refusal planner. Pending decisions survive container removal; creating
new destruction awards and acknowledging delivered effects remain follow-ups.

Acceptance:

- Bound award count/bytes, recipes and entropy. Bind one immutable decision to
  source UUID, transfer sequence/digest, owner region and authoritative spawn pose.
  Preserve zero-XP recipe unlocks and the exact fractional outcomes across retries.
- Atomically retain output-slot changes, cleared uses, pending XP/recipe effects
  and the terminal typed receipt. Rejection/capacity failure retains all credit.
  Removal must retain awards after the block/container entry disappears.
- Decode existing container/journal versions without inventing pending effects.
  Validate malformed/oversized/duplicate records and interrupted-write recovery.
- Retrying a typed action or replacing an owner must not append another award.
  Later materialization/recipe delivery requires durable acknowledgement before
  removing pending records; receipt compaction must preserve that guarantee.
- Targeted persistence/replay/stale-epoch/capacity tests and actual-client
  ordinary cooking/refusal/restart regression on an isolated frozen checkpoint.
  No XP entity, pickup, unlock or finished-furnace claim at this boundary.

Next: atomically materialize bounded region-owned orb records, synchronize native
orb metadata/motion/pickup, persist player XP and recipe grants, then admit earned
output with actual-client conservation and failure scenarios.

Implementation: `PendingCookingAwards` retains at most 256 immutable decisions,
512 KiB total and 107 recipes per decision, inside the existing 8 MiB container cap.
Identity binds region, source UUID, sequence and request digest; records retain
spawn pose, per-recipe amounts and consumed entropy. Decoding revalidates the native
proposal and the source's terminal receipt/high-water mark. Removing or rolling
back a needed receipt invalidates the snapshot. No delivered-effect removal API
exists yet. Live owner-fenced capture of the supplied bounded pose remains an
activation prerequisite; a cross-boundary pose needs orb-ownership handoff later.

`ContainerTransfers.plan_cooking_award/5` is an unused internal planner. Its whole
successor contains reduced output, cleared credit, pending effects and an applied
receipt. Replay returns the committed decision without using new entropy; refusals
retain slots/credit/earlier awards. The regular live planner still rejects earned
withdrawal. VMCCONTS4 embeds decisions; existing VMCCONTS1–3 bytes stay exact and
VMCMINE2 already journals the complete new snapshot without a separate XP file.

Checks: 88 affected tests (seed431813), then 14 owner checks (seed484455) and
focused malformed/legacy boundaries. Coverage includes prepared player intent,
writer death before source acknowledgement, replay/sealing, stale leases/epochs,
real region replacement, all eight interrupted three-file journal outcomes,
write failure/recovery, receipt loss, zero-XP unlocks, capacity and corrupt records.
Logs: `.local/pending-awards-{targeted,owner-tests,boundary-tests}.log`.
Original `d4e5e59` legacy hashes/proof: `.local/pending-awards-legacy-proof.{exs,json,log}`.

In-memory scaling probe: 30 samples after five warmups, ten schedulers, 107 recipes
per record. At 256 records the mixed snapshot is 414,126 bytes; encode p50/p95
21.329/27.824 ms, decode 52.676/88.197 ms. This excludes disk/gameplay/network and
does not compare equal-feature server capacity. Raw workload/source hashes/samples:
`.local/pending-awards-bench.{exs,json,log}`. No broad gate is due for this subticket.
