# VMC-066 — Tick pipeline on game time

Status: Done
Note: Coral blocks (scheduled ticks) and budding amethyst (random ticks) are live in play; client run passed on `fdca2df`.
Milestone: M1 foundations
Depends on: [VMC-063](VMC-063.md). Behaviours that use the ticks come with VMC-068
and later milestones.

Region owners tick every 50 ms, but each subsystem (items, cooking, orbs) keeps
its own wall-clock cadence, there is no game-tick counter shared by the phases,
no scheduled or random block ticks, and tests wait on real time (`Process.sleep`,
millisecond deadlines), which made suites flaky under concurrent load.

Scope: the region tick becomes one ordered pipeline driven by a per-region game
tick; scheduled and random block ticks exist as owner primitives; tests can step
the clock deterministically. No new block behaviour beyond what proves the
primitives.

Acceptance:

- One pipeline per region tick in fixed phases: scheduled block ticks due at this
  game tick, random ticks, items, cooking, orbs, then publication. Every phase
  receives the game tick; a late owner catches up at most a bounded number of
  ticks per wake (vanilla skips rather than bursting without bound).
- Scheduled ticks: per-region queue ordered by (due tick, priority, insertion),
  deduplicated per (position, block), bounded per region, persisted with the
  region (survive restart), executed only if the block at the position still
  matches.
- Random ticks: `randomTickSpeed` (3) positions per section per tick, only in
  sections that contain randomly ticking states (a generated fact), driven by a
  seeded per-region RNG.
- Steppable clock: `Region.step(owner, ticks)` runs the pipeline synchronously;
  with `:region_ticks, :manual` (per region) no timer fires. The item simulation
  suite steps instead of waiting on wall-clock ticks.
- No phase blocks on storage (VMC-063); backpressure defers commits.

Reference: vanilla `ServerLevel.tick` phase order, `LevelTicks` scheduling
(`ScheduledTick` ordering by trigger tick, priority, sub-tick order),
`ServerLevel.tickChunk` random ticks (`randomTickSpeed` game rule, default 3).

Progress (October 20, 2026):

- `Valimc.World.TickPipeline` runs each region tick in order: block ticks
  (scheduled, then random), items, cooking, orbs and their deliveries, on the
  owner's game tick. The existing timer cadence (no burst catch-up) is kept.
- `Valimc.World.ScheduledTicks`: queue ordered by (trigger tick, priority,
  insertion), deduplicated per (position, block), bounded at 65,536, run only if
  the block still matches; saved as a `{:ticks, entries}` region-log part with
  the periodic save and the shutdown tail, relative to the game tick.
- Random ticks: `RandomTickOracle` generates `priv/physics/random_ticking.json`
  (1,516 states, oracle stage `random_ticking`). A native sampler
  (`valimc_core::ColumnStore::random_ticks`) draws 3 positions per section,
  skips sections whose palette holds no handled state, and returns only hits:
  0.004 ms per region tick with a behaviour configured, against 1.46 ms for the
  first Elixir version (flat world, 64 chunks; `Region.step` timing).
- `Valimc.World.TickBehaviours`: behaviour modules name their states and return
  `{:set, ...}`/`{:schedule, ...}` effects, applied by the owner as one raw batch.
  None are configured yet (`:tick_behaviours`).
- Steppable clock: `Region.step/2` and `:region_ticks, :manual`; the item
  simulation region suite (0.3 s) steps instead of sleeping.
- `test/tick_pipeline_test.exs`: queue order, dedupe and dump/load; a test
  behaviour turns sampled grass to dirt and schedules stone two ticks later,
  across an owner restart.

- Tick reactions are optional `random_tick/4` and `scheduled_tick/4` callbacks of
  `Valimc.Block.Behaviour` (VMC-068), which also receive the owner's random
  source; `Valimc.Block.tick_states/0` (computed at compile time) feeds the
  owner's tick index, and `:tick_behaviours` only adds test modules.
- Shape updates: after any block commit (`apply_blocks`, so placement, mining,
  transfers and tick edits alike) the owner calls the optional `shape_update/4`
  for each edited position and its six neighbours in the region. It may only
  schedule ticks: the scheduling half of vanilla `updateShape`. Neighbours across
  a region border are not updated yet.
- `randomTickSpeed` is the `:random_tick_speed` setting (default 3,
  `VALIMC_RANDOM_TICK_SPEED` at runtime, 0..4096).
- First live behaviours, from `javap` of the pinned classes:
  - `Valimc.Block.Coral` (`CoralBlock`, five blocks): away from water (no
    neighbour whose fluid is water), a placed or disturbed coral block schedules
    a tick 60 + rand(40) ticks later and then becomes its `dead_` block.
  - `Valimc.Block.BuddingAmethyst` (`BuddingAmethystBlock`): one random tick in
    five picks a face in `Direction.values()` order, starts a small bud in air or
    full water (waterlogged), or grows a bud facing out of that face one stage
    (small, medium, large, cluster).
- Placement facts: `PlacementOracle` admits those two classes as plain
  placements (single default state, full block; CoralBlock's placement-time
  scheduling is the behaviour's `shape_update`). The stage now passes 1,622,154
  placement contexts and 3,510 consumption cases (190 plain items, 351 admitted).
- Fixed: a fresh region (no log yet) imported values without the `:ticks` part,
  so its first save with scheduled ticks crashed the region writer. The tick
  pipeline test now asserts the writer exits normally after that save.
- Fixed: owners tested tick callbacks with `function_exported?/3`, which is false
  for a module not loaded yet (test mode loads lazily; releases preload), so
  ticks depended on test order. `TickBehaviours.index/1` loads the modules.

Checks: `test/block_tick_behaviours_test.exs` (behaviour rules; coral dies
60–99 ticks after placement away from water and after its water is removed;
budding amethyst grows buds in a stepped owner), oracle stage `placement`, fast
suite 1,032.

Client run (October 20, 2026, frozen `fdca2df`, default tick speed,
`.local/client-tests/M1-ticks/`), all PASS:

- Placed tube and brain coral died about 4–5 s after placement in open air.
- Twelve budding amethyst grew about ten buds in 9.5 minutes. Buds formed on tops
  and sides, never underneath, each facing away from its block (F3 block state),
  and grew to medium and large/cluster.
- Dead coral and buds survived a server restart, and growth continued after it.
- Creative flight started and stopped 5/5 with held taps (50 ms press, 150 ms
  gap). An instant press and release in one frame is missed by the client's
  per-tick jump polling, which explains the earlier inconsistency. The server
  never overrides the flying flag.
- In survival, a fixture gave the player a furnace, raw gold and coal. Taking
  smelted gold spawned XP orbs that were collected at once: level 1 with 1/9 bar
  (8 XP) on the first take, nothing on the second (vanilla awards the stored
  recipe XP once). XP survived a reconnect.
- All server logs were free of errors and warnings.

Fixture note: a graceful stop leaves the last player save in the player WAL,
which the next start replays over the player file. Offline fixture edits
therefore need one start/stop with no join first.

and lava neighbours for cactus; from `javap` of the pinned `SugarCaneBlock` and
