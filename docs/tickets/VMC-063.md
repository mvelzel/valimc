# VMC-063 — Region log, group commit and one transaction engine (with VMC-064)

Status: In progress
Milestone: M1 foundations
Depends on: [VMC-062](VMC-062.md), [VMC-065](VMC-065.md). Covers VMC-064 as its
later steps.

## Problem

`RegionData` serializes every durable operation through one `item_pending` slot
(pickups, mining, placement, container exchanges, merges, handoffs, expiry,
checkpoints, cooking, orbs). Each waits for an fsync'd whole-file rewrite by
`Store`; mining/placement rewrite a journal plus the entire block image, items and
containers files. Item, cooking and orb ticks are skipped while a write is
pending; 18 entry points answer `:item_storage_busy`/`:mining_storage_busy`.
About 28 modules re-implement idempotent cross-owner transfers per feature, with
four receipt tables and five permit tables. Directories are never fsynced.

## Design

**Region log (VMC-063).** `r.X.Z/` holds checkpoints `ckpt.<lsn>` (section blobs,
items, containers, transaction tables, SHA-256 trailer) and append-only segments
`log.<base_lsn>` of CRC-checked frames
`<<len::32, crc32c::32, lsn::64, incarnation::32, n_ops::16, ops…>>`. Ops carry
absolute values (cells per chunk, item put/del, container put/del, receipts,
outbox put/clear, coalesced motion), so replay is idempotent. One frame is the
atomicity unit. The writer keeps the lease protocol, writes an `open` frame per
incarnation, drains queued frames with one `datasync`, rotates segments with a
directory fsync (a dirty-IO NIF), and compacts checkpoint plus sealed segments in
a worker (sections folded by a Rust dirty-CPU function). Recovery takes the
newest verified checkpoint and replays later frames; a torn tail of the last
segment is truncated, any other corruption refuses the load. v1 files import
into `ckpt.0` once.

**Group commit.** Operations apply to owner memory immediately; their op
records join the open batch and their external effects (replies, block rows and
fence, item views, world publications, deliveries, chunk replies) are held until
the batch is durable, then released in order. Nothing observable leaves the owner
before durability, so a crash recovers a prefix nobody has observed. Ticks never
wait; a bounded in-flight window returns a retryable `:storage_backpressure`.
Item motion stays volatile with its own published overlay.

**Transaction engine (VMC-064).** `%Txn{kind, source: {scope, id}, seq, digest}`
with a `Txn.Operation` behaviour (`decode/digest/admit/plan/apply`), one receipt
table (scoped, legacy digests byte-identical), one permit table invalidated by
revisions, one bounded outbox per destination, and one delivery worker per
source owner. Source clearing still requires destination receipt proof.

**Per-section fencing.** Chunk rows carry section revisions; permits and
collision verification fence on the sections they read.

## Acceptance (VMC-063 scope: steps 0–5 and 9; 6–8 are VMC-064)

- No tick or unrelated operation waits for an fsync: every durable write (items,
  blocks, containers, cooking, orbs) is adopted in owner memory and queued; only
  planning workers may hold the planning slot.
- The writer drains every queued frame into one append with one `datasync`
  (group commit); acknowledgements are released in frame order.
- In-flight depth is bounded per region; a full queue answers a retryable
  `:storage_backpressure` and ticks defer their commits.
- Write volume is bounded by the fsync rate: a drained batch writes merged cells
  and each full value once.
- Checkpoints do not stall the writer for unbounded time; log bytes are capped.
- Crash tests at every frame boundary recover a prefix that no client observed
  beyond; one effect sink is enforced by a leak test.
- Player saves are group-committed (no fsync per action).
- The durability decision for macOS (`F_FULLFSYNC`) is recorded.
- Client check of mining, placement, drops, pickups, chests, furnaces, reconnect
  and restart passes on the final checkpoint.

## Migration (each step green)

0. Test probe (`idle?`, `writing?`, durable watermark) replacing ~108 direct
   `item_pending` peeks in 26 test files.
1. `RegionLog` format, recovery and `fsync_dir` NIF as pure modules.
2. Store v2 backend with the same messages; v1 import; `MiningRecord` journal and
   its subset-of-three-files tests become obsolete.
3. Incremental ops and compaction; the 131,072-entry image cap disappears.
4. Durability sink at depth 1: writes stop blocking ticks and other operations.
   About 30 test files change from "busy" to "withheld until durable".
5. Pipelining (depth 4), footprint revalidation, backpressure; crash-at-every-
   frame tests.
6. Txn core with drops/death as the reference op, then pickup, mining,
   placement, container/experience; each removes its permits/transfers/request
   modules and their tests.
7. Region-sourced ops (handoff, cross-merge, orb spawn) on `Txn.Outbox`.
8. Per-section fencing.
9. PlayerStore group commit (one fsync per action today).

Risks: effect leaks past the sink (enforce one sink plus a leak test), chunk
encodes reading un-durable sections (tag with the durable watermark), macOS
`datasync` is not `F_FULLFSYNC`, receipt-table unification must not merge
sequence spaces, compaction stalls (cap log bytes), re-plan livelock (one retry).

## Progress

- Step 1 (October 19, 2026): `Valimc.World.RegionLog` (frames, segments with
  rotation, checkpoints, strict recovery with torn-tail truncation, incarnation
  frames) and the `fsync_dir` dirty-I/O NIF. `test/region_log_test.exs` covers
  round trips and truncation (property), corruption vs torn tail, reopen,
  checkpoint replacement and refusal of a damaged checkpoint, and rotation.
  Frames use CRC-32 (`:erlang.crc32`) and `term_to_binary` op lists. Not yet wired.
- Step 2 (October 19, 2026): `Store` keeps its message API but writes one log frame
  of full values per write; a mining/placement/container commit is a single atomic
  frame with one fsync (the separate `.mining` journal is gone). Legacy files import
  once into `ckpt` and are renamed `*.v1`. Cold reads use raw file I/O so one slow
  region cannot stall others' recovery. Behavior change: a failed commit frame
  leaves nothing durable, so a retry with the stale permit is rejected instead of
  replaying a journal. Tests read durable state through `Valimc.TestDisk` and
  inject writer failures with `break_writer/1`; journal-boundary tests were removed.
  Checks: `mix test.fast` 1,180 and socket suites 574 pass.
- Step 3 (October 19, 2026, blocks): block changes are logged as `{:cells, changes}`
  frames. Durable commits carry only their changed cells; raw edits accumulate in
  the owner's `unsaved` map, which the periodic save and flush send as cells and
  clear per acknowledged value. The owner no longer rebuilds the full sparse image
  per commit, and the 131,072-edit region cap is gone (sections are bounded by the
  Rust memory budget). Items and containers are still full values per frame.
- Step 4a (October 19, 2026, item writes): item operations (drops, deaths,
  pickups, merges, handoffs, cross-merges, expiry, rejection receipts) adopt their
  new item state in owner memory immediately and queue their frame; the single
  slot is freed, so further item operations and item ticks continue during the
  fsync. Held until the write is durable: the operation's reply, published item
  views, replies planned while writes are in flight, transfer and owner receipt
  queries (destination proof) and pickup grants (issued in order at durability).
  A failed write stops the owner with every waiting caller told the outcome is
  uncertain. A synchronous flush behind queued writes reports busy. Block,
  container and cooking commits keep the single slot for now (chunk encodes read
  live sections). Tests that asserted "busy" now assert held replies; durable state
  is read through `Valimc.TestDisk`, in-flight state through `Valimc.TestRegion`.
  Client check (October 20, 2026, `220dea1`): drops, Q/Ctrl+Q, mining pickup,
  merges, rapid drop-and-collect, reconnect and server restart all conserved
  counts with clean logs (`.local/client-tests/M1-items/`).
- Step 4b (October 19, 2026, block transfers): mining and placement transfers
  (including chest spills and chest metadata) adopt blocks and containers in owner
  memory and queue their frame like item writes. Held until durable: the reply,
  published block snapshots and client block updates for the adopted chunks,
  chunk packets and cache hits, `World.get_block` replies (client resync reads)
  and the already-applied/rejected replies. Each acknowledgement kind completes
  only its own kind of queued write. A failed write stops the owner and waiting
  callers get `:mining_commit_uncertain`. Container and cooking commits still use
  the single slot.
  Client check (October 20, 2026, `5b7cf61`): survival mining and placement, ~30 s
  of rapid break/place cycles, creative chest fill and spill (no chest item),
  reconnect and server restart all matched with conserved counts and clean logs
  (`.local/client-tests/M1-blocks/`). Removing an occupied furnace is still
  refused by design (VMC-034f), so the client sees the block restored.
- Step 4c (October 20, 2026, containers): container exchanges (deliver, admit,
  recover) and container block commits (creative chest creation and removal)
  adopt contents, permits and blocks at once and queue their frame. Every queued
  write has a kind (items, blocks, containers) that selects its acknowledgement,
  failure reply and stop reason, plus effects released at durability. Held: the
  reply, viewer notices, the orb pickup, container receipt proofs and chest or
  furnace menu openings while a world write is queued. Raw edits now also hold
  their client block updates behind queued world writes. Before this, a creative
  edit could reach clients ahead of an earlier transfer's update for the same
  block. Client check (October 20, 2026, `818b952`): chest and furnace exchanges,
  ~70 rapid shift-clicks, creative chest place/remove with spill, quick building,
  reconnect and server restart all matched with clean logs
  (`.local/client-tests/M1-containers/`). Chest placement is refused near region
  seams (`:cross_owner_chest`) and next to another chest (no double chests); both
  are existing scope limits, not regressions.
- Step 4d (October 20, 2026, cooking): cooking batches (lit changes, outputs),
  timer checkpoints and orb commits adopt their state and queue their frame;
  nothing durable uses the single slot any more, which now only guards planning
  workers. Orb snapshots are validated as storable before adoption. Cooking
  progress carries a generation: a durable frame clears `dirty` only when no
  progress changed after it was queued. Clean shutdown casts the volatile tail
  (item motion, cooking progress, raw cells) behind any queued frames instead of
  skipping it; `Store.close/2` waits for the writer to handle them.
- Step 5a/5b (October 20, 2026, writer and backpressure): the writer drains every
  commit cast already queued under its lease (up to 256) into one frame with one
  `datasync` and acknowledges them in arrival order. Frames are absolute, so the
  batch keeps merged cells and only the last items and containers, encoded once:
  write volume follows the fsync rate, not the operation rate. This replaces the
  incremental item/container ops of the original design; VMC-067 redefines item
  storage anyway. Joint commits no longer build, re-decode and hash a throwaway
  journal just to validate edit bounds. A failed append stops the writer (a torn
  frame may only be repaired by recovery); an invalid batch is refused without
  writing. Owners allow 64 queued writes; mutation entry points then answer a
  retryable `:storage_backpressure`, and ticks defer their commits.
