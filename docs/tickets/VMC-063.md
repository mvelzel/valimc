# VMC-063 — Region log, group commit and one transaction engine (with VMC-064)

Status: In progress
Milestone: M1 foundations
Depends on: [VMC-062](VMC-062.md), [VMC-065](VMC-065.md). Covers VMC-064 as its
later steps.

## Problem

`RegionData` serializes every durable operation through one `item_pending` slot
(pickups, mining, placement, container exchanges, merges, handoffs, expiry,
checkpoints, cooking, orbs). Each waits for an fsync'd whole-file rewrite by
`Store`; mining/placement rewrite a journal plus the entire block image, items and
containers files. Item, cooking and orb ticks are skipped while a write is
pending; 18 entry points answer `:item_storage_busy`/`:mining_storage_busy`.
About 28 modules re-implement idempotent cross-owner transfers per feature, with
four receipt tables and five permit tables. Directories are never fsynced.

## Design

**Region log (VMC-063).** `r.X.Z/` holds checkpoints `ckpt.<lsn>` (section blobs,
items, containers, transaction tables, SHA-256 trailer) and append-only segments
`log.<base_lsn>` of CRC-checked frames
`<<len::32, crc32c::32, lsn::64, incarnation::32, n_ops::16, ops…>>`. Ops carry
absolute values (cells per chunk, item put/del, container put/del, receipts,
outbox put/clear, coalesced motion), so replay is idempotent. One frame is the
atomicity unit. The writer keeps the lease protocol, writes an `open` frame per
incarnation, drains queued frames with one `datasync`, rotates segments with a
directory fsync (a dirty-IO NIF), and compacts checkpoint plus sealed segments in
a worker (sections folded by a Rust dirty-CPU function). Recovery takes the
newest verified checkpoint and replays later frames; a torn tail of the last
segment is truncated, any other corruption refuses the load. v1 files import
into `ckpt.0` once.

**Group commit.** Operations apply to owner memory immediately; their op
records join the open batch and their external effects (replies, block rows and
fence, item views, world publications, deliveries, chunk replies) are held until
the batch is durable, then released in order. Nothing observable leaves the owner
before durability, so a crash recovers a prefix nobody has observed. Ticks never
wait; a bounded in-flight window returns a retryable `:storage_backpressure`.
Item motion stays volatile with its own published overlay.

**Transaction engine (VMC-064).** `%Txn{kind, source: {scope, id}, seq, digest}`
with a `Txn.Operation` behaviour (`decode/digest/admit/plan/apply`), one receipt
table (scoped, legacy digests byte-identical), one permit table invalidated by
revisions, one bounded outbox per destination, and one delivery worker per
source owner. Source clearing still requires destination receipt proof.

**Per-section fencing.** Chunk rows carry section revisions; permits and
collision verification fence on the sections they read.

## Migration (each step green)

0. Test probe (`idle?`, `writing?`, durable watermark) replacing ~108 direct
   `item_pending` peeks in 26 test files.
1. `RegionLog` format, recovery and `fsync_dir` NIF as pure modules.
2. Store v2 backend with the same messages; v1 import; `MiningRecord` journal and
   its subset-of-three-files tests become obsolete.
3. Incremental ops and compaction; the 131,072-entry image cap disappears.
4. Durability sink at depth 1: writes stop blocking ticks and other operations.
   About 30 test files change from "busy" to "withheld until durable".
5. Pipelining (depth 4), footprint revalidation, backpressure; crash-at-every-
   frame tests.
6. Txn core with drops/death as the reference op, then pickup, mining,
   placement, container/experience; each removes its permits/transfers/request
   modules and their tests.
7. Region-sourced ops (handoff, cross-merge, orb spawn) on `Txn.Outbox`.
8. Per-section fencing.
9. PlayerStore group commit (one fsync per action today).

Risks: effect leaks past the sink (enforce one sink plus a leak test), chunk
encodes reading un-durable sections (tag with the durable watermark), macOS
`datasync` is not `F_FULLFSYNC`, receipt-table unification must not merge
sequence spaces, compaction stalls (cap log bytes), re-plan livelock (one retry).

## Progress

- Step 1 (October 19, 2026): `Valimc.World.RegionLog` (frames, segments with
  rotation, checkpoints, strict recovery with torn-tail truncation, incarnation
  frames) and the `fsync_dir` dirty-I/O NIF. `test/region_log_test.exs` covers
  round trips and truncation (property), corruption vs torn tail, reopen,
  checkpoint replacement and refusal of a damaged checkpoint, and rotation.
  Frames use CRC-32 (`:erlang.crc32`) and `term_to_binary` op lists. Not yet wired.
- Step 2 (October 19, 2026): `Store` keeps its message API but writes one log frame
  of full values per write; a mining/placement/container commit is a single atomic
  frame with one fsync (the separate `.mining` journal is gone). Legacy files import
  once into `ckpt` and are renamed `*.v1`. Cold reads use raw file I/O so one slow
  region cannot stall others' recovery. Behavior change: a failed commit frame
  leaves nothing durable, so a retry with the stale permit is rejected instead of
  replaying a journal. Tests read durable state through `Valimc.TestDisk` and
  inject writer failures with `break_writer/1`; journal-boundary tests were removed.
  Checks: `mix test.fast` 1,180 and socket suites 574 pass.
