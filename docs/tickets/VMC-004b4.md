# VMC-004b4 — Component schema engine and flat components

Status: Done
Milestone: M4
Parent: [VMC-004b](VMC-004b.md).

Each component so far has a hand-written codec in `ItemStack` and another in
`ItemData`. That does not scale to 88 more types. One declarative schema per
component now drives both formats: network read and write, data (NBT) read
and write, validation and the identity key that merging compares.

- `Valimc.Protocol.ComponentSchema` interprets schemas built from primitives
  (numbers with ranges, strings with length limits, identifiers, enums,
  registry entries and holders, holder sets, optionals, bounded lists,
  records with optional fields and defaults, dispatch on a type). It is pure,
  with no process.
- Enum names and built-in registry ids (sound events, attributes, villager
  types, block entity types and the rest) are generated from the pinned jar,
  not written by hand; synchronized registries use the ids ValiMC sends.
- A holder written inline (id 0 on the network) is refused explicitly: no
  vanilla item carries one and the client never needs to send one.
- Item defaults are extracted for every component type, deduplicated, so a
  patch equal to a default is redundant for every type.
- Values are plain data shaped like vanilla's data form: records are maps
  keyed by field name with defaults filled in, enums and registry entries are
  their names.

Acceptance: every flat component (no nested stacks, attribute modifiers or
gameplay dispatch) decodes and encodes in both formats. The `item_components`
stage: Mojang encodes every item prototype's components and constructed
values; ValiMC re-encodes the network bytes exactly, reads the data form to
the same value and writes it back; Mojang decodes both to equal values.
Malformed bytes, out-of-range values, unknown registry ids and tags fail.

## Result (October 31, 2026)

`ComponentSchema` and the schema table `ComponentSchemas` hold 61 component
types: every variant, colour and dye, the trims and banner patterns, fuels and
compostables (constant or a provider key), the weapon, reach, cooldown,
enchantable, repairable, use-effect and animation records, lodestone
trackers, fireworks and the rest of the flat types. `ItemStack` reads and
writes them on the network, `ItemData` in the data form, and both compare
them by the canonical encoding (NaN as Java's `Float.equals` sees it).

- `ItemMetadata` now encodes every component of every prototype against the
  client's registries (`NetworkRegistries`: built-ins plus the synchronized
  registries in identifier order, with the vanilla pack's tags), stores the
  3,779 distinct values once (`item_defaults.json`), and generates the enum
  ids and names (`component_types.json`) and the built-in registry ids
  (`builtin_registries.json`). The instrument's hand-computed id is gone.
- Lists cannot claim more elements than bytes remain; strings count UTF-16
  units as Java does; enums, registry ids and tags must exist; ranges are
  enforced on both formats; inline holders are refused.
- The `item_components` stage generates 3,948 distinct values across 102
  types (prototypes plus 70 constructed ones parsed by each type's own codec).
  ValiMC re-encodes the 248 values of its 61 schema types byte for byte, reads
  246 data forms to the same values, and Mojang decodes both back to equal
  values; its data tags equal Mojang's. The stage lists the types still
  without a schema; later slices empty that list.

Tests: `test/component_schema_test.exs` (bounds, NaN identity, both stack
formats, merging with defaults, SNBT); the item, stack identity, item data,
creative, SNBT and Anvil tests; stages `item_components`, `item_metadata`
(regenerated), `stack_identity`, `item`, `tooltip` and `item_hover`.
