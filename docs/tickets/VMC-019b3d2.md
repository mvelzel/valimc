## Scope and acceptance

Before: every negative creative slot is rejected, and the conserved-transfer gate
would discard a creative drop's following slot write. After: authorized negative
slots create one supported stationary item through the explicit source API, and
bounded deferred creative commands preserve packet order until the transfer clears.
This is creative preview behavior, not survival, item physics or full game modes.

- Decode bounded supported stacks, then check live owner permission. Any negative
  signed slot is a drop, 1..45 is a slot write; others cannot mutate inventory.
  Nil/air drops spawn nothing. Existing malformed/unsupported correction stays.
- Match vanilla's creative throttle: charge 20 when count is below 1480, decay one
  per 50 ms preview tick, including empty requests; denied requests add no charge.
  Use a connection-local pure counter and lazy tick accounting, no timer/process
  per drop. Future authoritative simulation ticks must supply its clock.
- One source outbox/delivery remains in flight. While creative creation or a
  normal save is pending, defer valid creative drops/writes in arrival order,
  bounded to 160 commands and 512 KiB including payload and fixed entry costs. Pin
  each admitted drop UUID/origin/destination once. Source slots remain unchanged
  by creation itself; subsequent slot writes are independent authorized actions.
  Drain at most 64 commands per callback with at most one scheduled continuation.
  Existing conserved-transfer gates continue to correct all inventory changes.
- Preserve valid client predictions during creative prepare/delivery and between
  queued pairs. Suppress intermediate old snapshots/slot acknowledgments; publish
  the completed command result when the queue becomes idle. Predictions confer
  no authority, and invalid/denied input still receives correction.
- Deferred commands are uncommitted, unacknowledged input until execution. They
  stop at disconnect; recovery replays only the actual committed intent. Accepted
  slot edits follow existing preview checkpoint/final-close durability. Do not
  claim a durable queue or acknowledged paired edits while their write is pending.
  Reject queue overflow without partial admission and correct predictions.
- Prepare/clear acknowledgment precedes the next creation. No-commit rejection
  can process independent queued writes; uncertain commit/deadline disconnects
  preserve the real intent. Busy saves drain on acknowledgment. Permission is
  checked at admission and execution, and revoked permission rejects queued work.
  Movement/chat/other sessions remain responsive throughout.
- Independent creative slot writes continue during an immutable normal checkpoint
  when no creation command precedes them. Only writes following deferred creation
  wait for that save, preserving the existing later-edits/final-close behavior.
- Tests exercise paired drop/write and multiple pairs in one TCP batch, exact
  component retention, negative bounds/empty/permission/invalid slots, throttle
  boundaries against Mojang's actual TickThrottler, count/byte queue limits,
  stalls/save admission/permission revocation/no-commit failure, disconnect and
  reconnect recovery. Format/full tests/release/Mojang oracle/audit pass.

## References and design

Pinned Mojang server SHA-1 `33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`:
`ServerGamePacketListenerImpl.handleSetCreativeModeSlot`, `TickThrottler`, and
the private client `CreativeModeInventoryScreen.slotClicked` inspection from
VMC-019b3d1. Negative-slot creation is independent of the inventory write, gated
by `hasInfiniteMaterials`; plugin cancellation is not a vanilla rule. The client
drop-then-write branch makes a blanket mutation freeze inappropriate for creation.
Throttle admission is strict `<1480`; a count of 1479 may become 1499. Empty
requests charge before the no-item drop method returns. The preview uses elapsed
50 ms deadlines, not a claim about stalled vanilla simulation tick progression.

SteelMC `f6fb4e49778c` keeps the creative drop counter on session state and tests
respawn retention; Pumpkin `b0c48b2d7688` separates creation and slot writes but
has no throttle in the inspected handler. Paper `a2d844f71e27` adds plugin events/
cancellation around those branches. Exact paths/conclusions are in VMC-019b3d1.
Original Elixir uses a small pure command queue/counter inside the socket owner,
existing per-player disk owner and bounded delivery jobs. No gameplay coordinator
or one-process-per-item arrangement is introduced. Queue admission is not durable
gameplay acceptance; authoritative source/receipt recovery remains unchanged.
