# VMC-019b2 — Durable player transfer outbox and checkpoint fencing

Status: Done — source API recovery validated. Updated: October 14, 2026.
Depends on VMC-019b1/005c1. VMC-019b/gameplay drops remain incomplete.

## Scope and acceptance

Before: player checkpoints can overwrite a reduced inventory, and have no pending
world-transfer intent. After: a leased player writer saves reduced inventory and
one pinned region/item batch together, preserving a monotonic source sequence.
Its changing session fence rejects older checkpoints/close calls. Clearing the
outbox requires the matching committed receipt from the destination region.

- Custom player file version 3 contains pose/inventory, unsigned 64-bit sequence
  and zero/one bounded outbox (region, 1–5 stable-UUID item records). Keep version
  1/2 read compatibility; ordinary sequence-zero/no-outbox snapshots can retain
  version 2. Validate checksums, UUID/version/data version, inventory/outbox byte
  budgets, target region/records, empty/unsupported stacks and sequence exhaustion.
  Derive source UUID/sequence/digest from the file rather than trusting duplicate
  fields. No player inventory permission/state-ID/drag/lease token persists.
- Only the leased owner can prepare/complete/checkpoint/close. A prepare derives
  the next source sequence and atomically saves after-inventory plus outbox.
  Validate before/after inventories and exact supported stack conservation:
  before = after + batch. No concurrent second outbox, nil-storage durability
  claim, sequence reuse/wrap or silent replacement of an existing intent.
- Rotate an ephemeral writer fence after preparation and completion. All normal
  checkpoints/close require the matching fence and no pending outbox. Writer-owned
  journal fields survive ordinary owner snapshots. Reject stale/pending saves;
  closing releases the lease without rolling old inventory over the committed
  file. A transfer write failure stops the writer with an uncertain result.
- Completion reads the destination's owner-fenced committed receipt, validates
  region/source/sequence/digest, then writes the same inventory with no outbox.
  Missing/conflicting/unavailable receipts leave the source intent intact.
  Receipts from a region without item storage cannot authorize clearing.
  Owner loss/reopen reads the actual file and uses a fresh lease fence. API requests and
  replies are asynchronous so future socket owners need not wait for disk work.
- Current login must reject a pending outbox without publishing player inventory
  or saving over it; release its writer lease. Automatic reconciliation and Q/
  menu/disconnect drop orchestration are the next slice, not silently discarded.
- Tests exercise migration/validation/bounds, conservation, authoritative fields,
  stale/foreign/fresh fences, pending/close preservation, destination proof,
  prepare/complete failure and lost-reply/reopen recovery, unrelated sessions and
  pending login rejection. Run format/full tests/release/full Mojang oracle/audit.

Actual Minecraft 26.3 via CUA: disconnect from the temporary world; use a clearly
identified offline source fixture with stone 7, atomically reduce to stone 4 plus
a stone-3 outbox. Attempt actual login and observe recovery-required rejection,
with file unchanged. Recover the fixture through its source/destination APIs,
rejoin and observe four in inventory and three as a stationary entity. Restart/
rejoin; verify no second entity and no restored removed inventory. Remove fixture
items and restore the originally empty inventory while preserving the advanced
source sequence/receipts. This is API-originated recovery, not actual Q/physics.

## Reference and design

Pinned Mojang 26.3 jar `33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`,
`ItemEntity.playerTouch`, `Player`/inventory removal and `PlayerDataStorage`:
inventory and entity lifecycles must conserve authoritative items. Private dumps
stay ignored. SteelMC `f6fb4e49778c` and Pumpkin `b0c48b2d7688` held-item removal/
spawn boundaries (recorded in VMC-019b1) motivate separate owner effects but do
not establish crash consistency. The outbox/fence protocol is original BEAM
recovery design. Existing per-UUID writers serialize/check disk outside sockets;
region owners prepare bounded pure jobs and commit receipts in their own writers.
There is no global gameplay transaction coordinator.

The future source orchestrator must admit one request, hold inventory mutations
until preparation is acknowledged, pin its IDs/region/sequence, retry only that
intent, and complete/recover it before another transfer. A missing reply is an
uncertain write outcome; inspect the leased source's actual recovered state.
Source/destination backups must be restored together. File sync/rename is not a
parent-directory fsync or power-loss durability qualification.
