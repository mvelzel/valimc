# VMC-072 — Container loot tables

Status: In progress
Milestone: M2 real worlds
Depends on: [VMC-025](VMC-025.md) (decoration and structures place chests,
barrels, dispensers, suspicious sand and gravel with loot tables),
[VMC-021](VMC-021.md) (imported containers keep unrolled loot tables).

Generated dungeons and structures, and imported worlds, hold containers whose
contents are a loot table and a seed (`LootTable`, `LootTableSeed`) until a
player opens them. ValiMC keeps such containers locked, so a dungeon chest in
a new world shows nothing when opened (the VMC-025d client run).

Scope: vanilla's loot tables from the data pack as a server loads them; the
entries, pools, rolls, conditions and functions chest, barrel, dispenser,
brushable-block and vault-free container tables use (including random
enchantments, set count/damage/components, potions and stews, exploration
maps through the structure search); `RandomizableContainer.unpackLootTable` on
open, break or hopper access with the stored seed (a fresh one when none is
stored), filling slots as `LootTable.fill` does (shuffled split stacks); the
container then opens as an ordinary owned container; brushing suspicious
blocks where brushing exists.

Acceptance:

- A loot oracle fills containers from vanilla's tables with given seeds and
  luck: every chest, barrel and dispenser table in the pack, many seeds, and
  ValiMC's contents equal vanilla's slot for slot with item components.
- Dungeon, temple, mineshaft, village and shipwreck chests in a new vanilla
  world open with vanilla's contents for their seed; imported unrolled chests
  open too; reopening does not roll again; a restart keeps the rolled items.
- Actual client: open generated chests in several structures.

## Slices

- VMC-072a: the loot engine and its parity (Foundation).
- VMC-072b: chests unpack their loot on open and break, then become ordinary
  owned containers; generated and imported unrolled chests open.
- VMC-072c: exploration maps in play (map ids and saved map data, the
  structure search that `/locate` uses). Until then, an exploration map
  function finds no structure and leaves a plain map, as vanilla does when
  its search fails.
- Barrels, dispensers, trapped and double chests, decorated pots, hoppers
  and brushing unpack through the same call once those blocks exist; they
  belong to the tickets that add them.

## VMC-072a — loot engine and parity (October 21, 2026)

- Facts (`LootOracle facts`, stage `loot`): `priv/loot/tables.json` holds
  the 69 loot tables that chests, barrels, dispensers, decorated pots and
  brushable blocks name in the vanilla data pack, and the tables they nest,
  loaded as a server loads them (`WorldLoader` order: static registries'
  tags, world registries, reloadable registries) and written back through
  `LootTable.DIRECT_CODEC`. `priv/loot/registries.json` holds what evaluation
  reads: enchantments in registry order (weight, maximum level, cost
  formulas, supported and primary items resolved, exclusive set), per item
  its stack size, damage, damageability and enchantability, the
  instantaneous effects, and the enchantment, instrument, biome, structure
  and item tags in iteration order. The network tag facts sort their
  members, so they cannot stand in for the item tags.
- `valimc_core::loot` (pure Rust, `ResourceArc` in `Valimc.Loot`): tables,
  pools (rolls and luck-scaled bonus rolls), item, empty, loot table
  (expanded or not), tag (expanded or not), dynamic, alternatives,
  sequence and group entries, with weights and quality; the random chance,
  inverted, all of, any of and location (biome) conditions; and the
  functions the pack uses: set count, set damage, enchant randomly, enchant
  with levels, set enchantments, set potion, set stew effect, set ominous
  bottle amplifier, set instrument, set name, filtered, discard,
  exploration map and sequences. Unknown types fail when the facts load. The
  `slots` entry reads an entity and no container table can use it.
- Draw order follows vanilla's decorated consumers: each item passes through
  its entry's modifiers (innermost first), then the pool's and the table's,
  as it streams out, so nested tables draw in vanilla's order. A container
  fill splits stacks at their maximum, shuffles the empty slots and splits
  stacks into the free ones as `LootTable.fill` and `shuffleAndSplitItems`
  do. Enchanting follows `EnchantmentHelper.selectEnchantment` (float cost
  span rounded as `Math.round(float)`, books becoming enchanted books with
  stored enchantments).
- `Valimc.Loot.fill/4` is `unpackLootTable` on an empty container: the
  stored seed through a legacy random, or a fresh random seed when none is
  stored (vanilla then draws from the world's random sequence for the
  table, which ValiMC does not keep; the distribution is the same); the
  origin is the block centre; the caller passes the biome there, the
  structure an exploration map would find and the next free map id.
  `Valimc.Loot.items/4` is a brushable block's roll. Stacks come back as
  `ItemStack`s without patch entries equal to the item's defaults, as
  vanilla's patch drops them.
- Item components loot writes, network and data format: suspicious stew
  effects, instruments, ominous bottle amplifiers, map ids and map
  decorations (persistent only, never sent to the client). `ItemMetadata`
  now records the defaults of these components; the goat horn's default
  instrument is a data-driven holder, encoded by its index in the loaded
  registry.
- Oracle: `LootOracle cases` fills every table 40 times (seeds from a fixed
  `java.util.Random`; luck 0, 1.5 and −1; five biomes; random origins),
  with a probe level whose structure search answers from the seed (a third
  find nothing) and whose map ids count from 0, plus 200 fills each of two
  synthetic tables decoded by vanilla's codec for the entry kinds and
  modifier nesting no container table uses (tag entries both ways,
  alternatives, sequences, groups, dynamic entries, nested composites with
  modifiers, all of and any of). Brushable tables use the vault parameter
  set, since archaeology's set requires a player and tool those tables do
  not read. Item defaults bind to the loaded registries, as
  `ReloadableServerResources` binds them. `check_loot.exs` compares each
  fill slot for slot through the persistent item codec (enchantment maps as
  maps; their network order follows a hash map).
- Classes read (Vineflower over the pinned jar, ignored
  `research/disassembly/vmc023/src15`–`src17`): `LootTable`, `LootPool`, the
  entry classes (`LootPoolEntryContainer`, `UniformContainerBase`,
  `ExpandableContainerBase`, `SingleEntryContainerBase`,
  `CompositeEntryBase`, `AlternativesEntry`, `SequentialEntry`,
  `EntryGroup`, `NestedLootTable`, `TagEntry`, `DynamicLoot`, `LootItem`,
  `EmptyLootItem`), the conditions and functions above,
  `LootItemFunction.decorate`, `LootContext`, `EnchantmentHelper`,
  `Enchantment`, `ItemEnchantments`, `ExplorationMapFunction`, `MapItem`,
  `MapItemSavedData`, `RandomizableContainer`, `Util.shuffle`,
  `Mth.nextInt`, `ReloadableServerResources` and `DataComponentInitializers`.

Evidence:

- `LootOracle facts`: 69 tables (all named by containers), 43 enchantments,
  1,658 items; the facts equal `priv/loot` (stage `loot`).
- `LootOracle cases` and `check_loot.exs`: 3,160 vanilla container fills
  over 69 pack and 2 synthetic tables (28,327 stacks), all equal.
- Stages `loot`, `item_metadata`, `stack_identity`, `chest_loot`,
  `mining_loot`, `random_mining_loot` and `cooking_loot` pass.
- A fill through the NIF takes a median 11 µs (simple dungeon) to 23 µs
  (ancient city) over 5,000 seeds; parsing the facts takes 24 ms once per
  VM. Measured on a machine at load average 66, so tails are preemption.
