# VMC-005c1 — Bounded supported inventory persistence

Status: Done
Note: Done — supported preview recovery validated. Updated: October 14, 2026. Depends on VMC-005a/004b1/003a. Parent VMC-005c and complete vanilla player persistence remain incomplete.

## Scope and acceptance

Before: UUID-leased pose files survive reconnect; inventories are discarded.
After: the same writer checkpoints one immutable pose/inventory snapshot and
restores supported contents, selection and preserved components before play.

- Extend the custom `.pose` file with a checksummed version 2 schema pinned to
  data version 5023. Fixed slot order covers 1..45 plus carried stack and selected
  hotbar. The virtual result is never serialized as a real item. Enforce the
  existing 512 KiB inventory byte limit and 65,536-byte per-stack codec limit.
  Bound file reading before allocation/decoding; reject trailing/truncated bytes,
  bad checksums/UUID/version/data version, invalid selections and unsupported
  stacks. Preserve corrupt files and reject only the affected login.
- Read old version 1 poses without changing files during login/configuration;
  migrate on the next valid checkpoint/final save. New identities start empty.
  Permissions, gestures and menu state IDs are runtime state, not saved authority.
- Socket owners capture immutable snapshots; item encoding and disk I/O stay in
  their existing UUID-leased writer. Keep one pending checkpoint and the deadline.
  Preserve lease fencing, final close, failure isolation and bounded saves.
- Restore before inventory/selection/cursor initialization. Accepted inventory
  operations preceding a rejected/malformed later frame must survive final save.
  Rejected configuration must never overwrite an existing snapshot.
- Regression checks cover patched/scalar/NBT/removal contents across ordinary,
  armor/offhand/hotbar slots, selection, supported carried/grid retention, empty
  slots, invalid/oversized files, legacy migration, writer stalls/CAS lease fencing,
  failed writes, reconnect, supervised shutdown and earlier accepted batched edits.
  Run format, full tests, production release, full Mojang protocol oracle and audit.

Actual Minecraft 26.3 through CUA: seed supported patched stone/egg/armor/offhand
contents using accepted development fixture paths; verify the current UI. Change
hotbar selection with actual keyboard input, disconnect/rejoin, verify selection
and exact saved stacks/patches. Gracefully restart the connected release, rejoin,
verify again. Use a supported carried/grid fixture to check reconnect preservation
and cancel gesture restoration. Exercise malformed-save rejection while another
identity stays healthy through TCP; actual client rejection/recovery as feasible.
Preserve the user's existing temporary world and leave clean fixture inventory.

## Boundaries and references

Mojang 26.3 jar SHA-1 `33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`:
`Player.readAdditionalSaveData/addAdditionalSaveData` load/save inventory and
SelectedItemSlot; `Inventory.load/save` uses slot-tagged item codecs;
`PlayerDataStorage` and `PlayerList` define UUID save/load timing. Private bytecode
under ignored `research/disassembly/` remains the compatibility reference.
Current custom files do not claim vanilla NBT/slot-number/import compatibility.
SteelMC `f6fb4e49778c`, `player_data_storage/file_storage.rs`, separates synced
replacement from lease/serialization. Pumpkin `b0c48b2d7688`,
`pumpkin-world/src/data/player_data.rs`, supplies another UUID storage boundary.
Our existing supervised session writer is retained, not their locks/cache design.

Carried/grid items are retained as preview recovery state while disconnected-menu
return/world-drop cleanup remains VMC-005b2d2. This deliberately avoids losing
owned items; it is not vanilla disconnect/menu lifecycle parity. Virtual result 0
must be empty. Drag state, state IDs and creative permissions are freshly created
on login. Supported component patches/removals survive exactly; equal-default
normalization and other component types remain VMC-004b2.

Checkpoints/final writes use synced temporary-file replacement. There is still no
transaction ledger, parent-directory fsync guarantee, vanilla data fixing or
hard-crash durability for acknowledged gameplay effects. Killed owners/VMs may
lose state since the last checkpoint. This must not authorize consuming inventory
into ephemeral VMC-018b scene items. Recovery transactions/persistent entities are
subsequent required foundations for gameplay drops/pickups.
