# VMC-025 — Features and structures

Status: In progress
Milestone: M2 real worlds
Depends on: [VMC-024](VMC-024.md) (terrain through carvers, generated live).

Generated worlds have vanilla's terrain but no trees, plants, ores outside the
veins, lakes, springs, geodes or structures. Vanilla adds them in the features
step (`ChunkGenerator.applyBiomeDecoration`), which decorates one chunk while
its eight neighbours are at least terrain, and may write into all nine. This
ticket brings that step, first as parity-tested foundations, then live.

The 26.3 overworld decorates in 11 steps with 171 placed features (178
features over 33 feature types: 33 tree configurations, 31 simple blocks, 24
ores, selectors, disks, springs, lakes, geodes, dripstone and sulfur
speleothems, vegetation patches, fossils, monster rooms and more) and 13
placement modifiers. 26.3 merged configured features into features (a
feature is a typed record in `worldgen/feature`) and added a
`worldgen/block_state_provider` registry and an explicit placer
(`FeaturePlacer`) that applies placement modifiers depth first.

Behaviour comes from the pinned jar (`javap -c` and the private Vineflower
decompilation recorded in [VMC-023](VMC-023.md), now also the feature,
placement, structure and chunk status packages) and from oracles that run
vanilla's own feature classes. The Rust is original.

Acceptance (parent):

- For several seeds and chunks near and far from the origin, a decorated
  chunk area equals vanilla's block for block (with block entities, fluid
  ticks and post-processing marks) when both decorate the same chunks in the
  same order.
- New worlds generate features and structures live, each chunk decorated
  once, and a vanilla client sees them; nothing is cut off at chunk or region
  borders.
- Decoration throughput is benchmarked against vanilla and Pumpkin on matched
  chunks and stays in Pumpkin's range.

## Design notes

- Order dependence: decorations of neighbouring chunks overlap, so a chunk's
  final contents depend on the order in which its neighbours were decorated.
  Vanilla decorates each chunk once in whatever order its chunk system
  reaches it. Parity is therefore defined for a given order: the oracle and
  ValiMC decorate the same chunks in the same order. Live generation (025d)
  keeps vanilla's invariants (each chunk decorated once, writes only within
  its 3 × 3, a chunk final once its whole 3 × 3 is decorated) rather than
  vanilla's incidental order.
- The decoration oracle cannot build a `WorldGenRegion` without a running
  server, so it implements vanilla's `WorldGenLevel` interface as a proxy over
  proto chunks, following `WorldGenRegion` (write zone, `setBlock`
  post-processing and block entity handling, heightmaps through the proto
  chunks, biomes through `BiomeManager` over the chunks' stored biomes), and
  fails on any method a feature calls that it does not implement. The
  features, placement modifiers and placer are vanilla's own classes.

## VMC-025a — decoration pipeline and first features (October 20, 2026)

- Facts (stage `worldgen_facts`): `features.json` (240), `placed_features.json`
  (273), `block_state_providers.json` (8), each biome's placed features per
  step in `biomes.json`, and `feature_order.json`: per biome source
  (overworld and nether presets, the End) the placed features of each step in
  the order vanilla's own `FeatureSorter` gives them, whose index seeds each
  feature. `blocks.json` (`WorldgenBlocksOracle`): per state `isAir`,
  `canBeReplaced()`, legacy `isSolid`, `liquid()`, block entities, sturdy
  full faces, post-processing positions (the block itself, or above it for
  soul sand and magma), and liquid, double plant and mossy carpet blocks; a
  state whose sturdiness reads the level (moving piston, shulker boxes) has
  none.
- Survival (stage `worldgen_survival`, `SupportOracle worldgen`,
  `priv/worldgen/survival.json`): decoration checks `canSurvive` before
  placing, so the block's own position is an input like its neighbours (tall
  seagrass needs water there), under the light of unlit chunks (sky 15, block
  0). The oracle derives per-state rules with the support facts' partitions
  and tables (VMC-029c), seeds each cell's search with common states, and
  validates every rule on random neighbourhoods (936,832, all equal): 7,326
  states, 200 rules; chorus plants are excluded (more than eight cells). The
  physics support facts are unchanged.
- `valimc_core::worldgen`:
  - `random`: `WorldgenRandom` over Xoroshiro (the legacy algorithms on
    Xoroshiro's bits, the Gaussian kept across reseeds) with decoration and
    feature seeds; stage `worldgen_random` gains 200 such traces.
  - `providers`: int, float and height providers and weighted lists, shared
    with the carvers.
  - `blocks`: the block registry with properties, tags and the flags above.
  - `region`: proto chunks at status `terrain` (heightmaps primed from the
    terrain; the final four updated on writes, the worldgen two frozen, as
    `ProtoChunk` does; writes into an all-air section skipped for air;
    post-processing marks; ticks stored once per position and type at delay
    0; pending block entities) and the region a chunk is decorated through,
    following `WorldGenRegion`: the 3 × 3 write zone, reads up to the area,
    chunk biomes of the 3 × 3 through the fuzzy zoom.
  - `predicate`, `state_provider`, `placement`: every 26.3 block predicate,
    rule test, block state provider and placement modifier the overworld uses
    (`cuboid` waits for its feature), and `FeaturePlacer` (modifiers depth
    first).
  - `feature`: the decoration registry and `applyBiomeDecoration` without
    structures (decoration seed from the chunk origin, possible biomes of the
    3 × 3, vanilla's feature order and seeds, the biome check against each
    biome's placed features), and the features ore (written straight into
    sections, as vanilla), disk, spring, simple block (double plants with
    waterlogging), the random, simple random, weighted and boolean selectors,
    sequence, block column, lake, freeze top layer, blue ice and block blob.
    Other types parse as unsupported and fail if placed.
  - `Worldgen::decorate_area`, NIF `worldgen_decorate`.
- Stage `worldgen_decoration` (`DecorationOracle`, `check_decoration.exs`):
  for three seeds, five areas each (two near the origin, two within 32,000
  blocks, one far out), the 5 × 5 chunks get vanilla's terrain, the 3 × 3 in
  the middle are decorated in order (Z outer, X inner) by vanilla's own
  features, with every placed feature whose types this slice implements: 115
  of the overworld's 171 (all ores, disks, springs, lakes, flowers, grass and
  other plants, seagrass, sugar cane, cacti, kelp, mushrooms, blue ice,
  freezing). All 36,864,000 blocks, 19,081 post-processing marks, 756
  scheduled ticks and both block entities equal vanilla's; a changed block
  fails. The oracle's level implements `WorldGenLevel` over proto chunks after
  `WorldGenRegion` (lit as unlit chunks are, fluid tags bound as a server
  binds them); with every placed feature included, its loop gives the same
  area as vanilla's own `applyBiomeDecoration`, which the oracle checks on
  its first area.
- Ores take `Math.sin` and `Math.cos` of a float direction (2^24 values).
  `Math` may differ between JVMs within an ulp: this aarch64 HotSpot differs
  from `StrictMath` on 1,884,807 of them, and Rust's platform functions from
  this JVM on 1,658,311 (sine) and 1,191,188 (cosine), always by one ulp. A
  vein can only differ where a coordinate lands within about 1e-15 of a block
  boundary; none did in the parity areas (`DecorationOracle trig` measures
  it).
- Benchmark (`bench/worldgen_decoration.exs`, `DecorationOracle … bench`; one
  thread, seed 20261020, 64 chunks decorated in a 10 × 10 terrain area,
  terrain excluded; raw results in ignored `bench/results/`): the 115 placed
  features take a median 0.48 ms per chunk in ValiMC against 1.14 ms in
  vanilla through the oracle's level. Pumpkin's features stage runs every
  feature and structure, so its comparison waits for VMC-025c.
