# VMC-025 — Features and structures

Status: Done
Milestone: M2 real worlds
Depends on: [VMC-024](VMC-024.md) (terrain through carvers, generated live).

Generated worlds have vanilla's terrain but no trees, plants, ores outside the
veins, lakes, springs, geodes or structures. Vanilla adds them in the features
step (`ChunkGenerator.applyBiomeDecoration`), which decorates one chunk while
its eight neighbours are at least terrain, and may write into all nine. This
ticket brings that step, first as parity-tested foundations, then live.

The 26.3 overworld decorates in 11 steps with 171 placed features (178
features over 33 feature types: 33 tree configurations, 31 simple blocks, 24
ores, selectors, disks, springs, lakes, geodes, dripstone and sulfur
speleothems, vegetation patches, fossils, monster rooms and more) and 13
placement modifiers. 26.3 merged configured features into features (a
feature is a typed record in `worldgen/feature`) and added a
`worldgen/block_state_provider` registry and an explicit placer
(`FeaturePlacer`) that applies placement modifiers depth first.

Behaviour comes from the pinned jar (`javap -c` and the private Vineflower
decompilation recorded in [VMC-023](VMC-023.md), now also the feature,
placement, structure and chunk status packages) and from oracles that run
vanilla's own feature classes. The Rust is original.

Acceptance (parent):

- For several seeds and chunks near and far from the origin, a decorated
  chunk area equals vanilla's block for block (with block entities, fluid
  ticks and post-processing marks) when both decorate the same chunks in the
  same order.
- New worlds generate features and structures live, each chunk decorated
  once, and a vanilla client sees them; nothing is cut off at chunk or region
  borders.
- Decoration throughput is benchmarked against vanilla and Pumpkin on matched
  chunks and stays in Pumpkin's range.

## Design notes

- Order dependence: decorations of neighbouring chunks overlap, so a chunk's
  final contents depend on the order in which its neighbours were decorated.
  Vanilla decorates each chunk once in whatever order its chunk system
  reaches it. Parity is therefore defined for a given order: the oracle and
  ValiMC decorate the same chunks in the same order. Live generation (025d)
  keeps vanilla's invariants (each chunk decorated once, writes only within
  its 3 × 3, a chunk final once its whole 3 × 3 is decorated) rather than
  vanilla's incidental order.
- The decoration oracle cannot build a `WorldGenRegion` without a running
  server, so it implements vanilla's `WorldGenLevel` interface as a proxy over
  proto chunks, following `WorldGenRegion` (write zone, `setBlock`
  post-processing and block entity handling, heightmaps through the proto
  chunks, biomes through `BiomeManager` over the chunks' stored biomes), and
  fails on any method a feature calls that it does not implement. The
  features, placement modifiers and placer are vanilla's own classes.
- The worldgen registries are the ones a server loads from the vanilla data
  pack, not the ones vanilla's code builds (`VanillaRegistries`): the pack's
  JSON is what the code's values encode to, and where a codec writes one
  field from another the two differ. The cherry foliage placer writes its
  corner hole chance from its wide bottom layer hole chance, so the pack (and
  every server) uses 0.25 where the code says 0.5.

## VMC-025d — features live (plan, October 21, 2026)

Vanilla decorates a chunk once its eight neighbours have terrain, writing into
all nine, and a chunk is full (sent, simulated) once its own 3 × 3 is
decorated. Live ValiMC keeps those invariants over durable proto chunks. A
measurement fixes the transaction's footprint: with all 171 placed features,
918 decorations in 102 random areas never read a block or heightmap outside
the decorated chunk's 3 × 3 (the region's reads limited to distance 1 never
faulted), so a decoration's inputs and outputs are its 3 × 3. It follows that
a chunk that is final is never read or written by a later decoration: if
chunk `X` is final, every chunk of its 3 × 3 is decorated, and a later
decoration `D` touching `X` would lie in that 3 × 3.

Statuses: `terrain` (a pure function of seed and position, so not stored
until a decoration changes it), `decorated`, and `final` (its 3 × 3
decorated). Order: chunks are decorated in batches per region (below), each
batch Z outer, X inner; batches of overlapping areas serialize in whatever
order they acquire their locks, as vanilla's order depends on its chunk
system.

Ownership:

- One proto owner per region key (`Valimc.Worldgen.Proto`, started on
  demand, separate from the live region owner) holds the region's non-final
  proto chunks as immutable encoded binaries, their statuses, the set of its
  final chunks, its lock table and its outbox, and writes them to its own
  `RegionLog` (`gen/r.X.Z`) through a writer process with group commit.
  Terrain and decoration run in a bounded worker pool on dirty schedulers;
  the native worldgen state becomes a pool of per-thread states so
  generations of one seed run in parallel.
- The live region owner of a decorated world asks its proto owner for its
  64 final chunks when it loads, persists their column images, block
  entities, block ticks and pending post-processing data in one frame, then
  tells the proto owner, which drops them.

The finalize transaction (region `R`, coordinated by `R`'s proto owner;
presumed abort with durable prepare):

1. Lock, in participant key order (no deadlock): each of the nine proto
   owners with chunks in the 12 × 12 around `R` generates their missing
   terrain, reports final chunks, and locks the rest for the transaction
   (`Txn.Permits` kind `:generation`). Foreign locks are durable before the
   grant is answered; a conflicting request waits in a bounded queue.
2. Decorate every undecorated chunk of the 10 × 10 around `R`, Z outer and X
   inner, in one native call over the locked images; `R`'s chunks are now
   final.
3. Commit: one durable frame in `R`'s log with its own new images, final
   set and an outbox entry per foreign participant.
4. Deliver (`Txn.Delivery`): each participant applies its part idempotently
   (`Txn.Receipts`, source `R`, sequence from `R`'s log incarnation and
   transaction count, digest of the part), durably, and releases the lock;
   the outbox entry clears on proof.

Recovery: a participant restarting with a durable lock asks the coordinator
(starting it if needed): committed parts are redelivered, a transaction its
current incarnation is still running is awaited, anything else is aborted
and the lock released. A coordinator restarting redelivers its outbox.
Transaction identities carry the log incarnation, so an aborted transaction
can never be confused with a later one.

Live state: column images with protocol biomes; created block entities
(dungeon chests and brushable blocks with their loot table and seed,
spawners with their mob, beehives with their bees) as vanilla's saved NBT in
the region's block entities; block ticks into the region's scheduled ticks
at delay 0 when the block still matches; fluid ticks and post-processing
marks stored per chunk until fluids exist (VMC-031). New vanilla worlds
record that they are decorated; earlier generated worlds keep terrain only.

## VMC-025d1 — proto chunks and parallel generation (October 21, 2026)

- `worldgen::proto`: a proto chunk as an immutable binary: its blocks and
  chunk biomes as a column image, all six heightmaps (the worldgen two stay
  frozen at the terrain's), post-processing marks, block and fluid ticks,
  block entity positions and created block entities. Proto chunks track
  whether a decoration wrote into them, so only those are encoded again.
- `region`: an area may leave out chunks (live generation holds only the
  non-final ones). A decoration's own 3 × 3 must be held; a block or
  heightmap read of a chunk the area does not hold sees an empty chunk, as
  vanilla's region sees a neighbour still before the noise step, and is
  counted (none occurred).
- Beehives keep their bees: each occupant's ticks in the hive from the
  decorator's draws. `DecorationOracle` reports them; stage
  `worldgen_decoration` passes again with them (all 50 areas).
- NIFs on dirty schedulers: `worldgen_proto_terrain`,
  `worldgen_proto_decorate` (every placed feature, in a given order),
  `worldgen_proto_full` (the column image with protocol biomes, the first
  free Y above the highest motion-blocking non-leaf block per column, block
  entities, block ticks as the state where the block still matches, fluid
  ticks, marks) and `worldgen_proto_inspect` (parity).
- The worldgen state is a pool: each call leases a state of its own, so
  generations of one seed run in parallel instead of taking turns on one
  lock (results agree with serial generation).
- Tests (`test/worldgen_proto_test.exs`): three areas decorated through
  encoded proto chunks equal `worldgen_decorate` (blocks, marks, ticks, block
  entities); full columns hold the decorated blocks; parallel and serial
  terrain agree.

## VMC-025d4 — finalize transactions in parallel (October 21, 2026)

- The finalize transaction no longer takes its nine owners' locks one at a
  time while holding the earlier ones. It asks all nine for their terrain
  first (no locks), then for all locks at once; an owner grants at once or
  answers busy, and on any busy answer the coordinator gives every lock back
  and tries again after a random delay growing with consecutive busy
  attempts (1 to 256 ms), or a few milliseconds after a busy owner releases
  a lock of a real transaction. Busy attempts do not count as failures.
  Requests go out with `:gen_server.send_request/4`, so the coordinator
  never waits on a participant and needs no worker per request.
- A lock is not durable when granted: each foreign owner that locked chunks
  writes its lock frame when the coordinator prepares it, while the
  decoration runs, and the coordinator commits once both are done. A lock
  not yet durable is released when its coordinator dies (the transaction
  cannot have committed without it); a durable one asks the coordinator as
  before. The periodic resolve pass also asks about locks not yet durable,
  in case a release was lost.
- Decoration and full chunks run in a pool of their own
  (`Valimc.DecorationWorkers`), and a decoration that finds it full waits
  (holding its locks) instead of aborting the transaction.
- Terrain priority: every terrain request carries when its region first
  tried to finalize; an owner's queue runs earliest first, and
  `Valimc.Worldgen.TerrainBoard` (a public ordered ETS table of each owner's
  earliest queued priority) lets only the owners among the most urgent, as
  many as there are dirty schedulers, start terrain jobs. Areas so complete
  in the order their transactions started and decorate while later terrain
  is generated; in play, the regions a player asked for first come first.
  Entries of dead owners are skipped and removed by readers.
- Tests (`test/worldgen_proto_owner_test.exs`): three regions in a row
  finalized at once equal one of the four orders the middle one's conflicts
  allow; the crash tests wait for a durable (prepared) lock instead of a
  granted one. Teardown kills owners until none of the test's keys is left,
  since a transaction still running starts the owners it asks (one restarted
  that way kept the previous test's world and failed a later test).
- Benchmark (`bench/worldgen_live.exs` and `bench/worldgen_live_trace.exs`,

## VMC-025f5 — structures live (October 21, 2026)

- A world generates structures when its settings say so
  (`generate_structures`: true for new worlds and legacy vanilla worlds);
  `Generator.spec` carries the flag to the proto owners of every dimension.
  Their terrain then has each chunk's beards from the starts that reference
  it, and their decoration places, in each step before its features, the
  structures whose starts reference the chunk, as `applyBiomeDecoration`
  does with structures on.
- Starts are not stored: they are pure functions of the seed, the settings
  and the data packs, so a worldgen state makes a chunk's starts once (kept
  for up to 16,384 chunks per state) and every transaction sees the same
  ones, with references made from them per chunk. Placement changes a start
  in two places where vanilla's chunk order shows through:
  - A desert pyramid, jungle temple or swamp hut settles its height in the
    first chunk that places it, from the surface as decoration left it.
    Live generation settles it before any placement from the terrain's
    frozen `WORLD_SURFACE_WG` heights over the whole piece (the lowest,
    lowered by 0–2 from a random of the seed and the start's chunk, for a
    desert pyramid; the mean for the others; columns past the transaction's
    area from the same pure terrain), so every chunk places a temple at one
    height in any order. Shipwrecks and ocean ruins read frozen worldgen
    heightmaps, buried treasure is one chunk, and other pieces carry their
    height from generation.
  - A mineshaft spider corridor places its one cave spider spawner in the
    first chunk with a free spot. Within a transaction that holds; between
    transactions the flag is kept since VMC-025f6.
- Template block entities reach the region as their template's NBT with
  the loot table and seed that placement wrote, keeping the template's
  components (`FullChunk`). Template entities and minecart chests stay in
  the proto chunks as type, position and yaw until entities exist (proto
  image version 3, which also stores template NBT and any entity type); a
  full chunk leaves them out.
- Found by the live stage: a ruined portal's netherrack replaces any block
  but plain air (`is(Blocks.AIR)`), so it spreads into a mineshaft's cave
  air; ValiMC had kept all air. And `Math.sin`/`cos` are JVM-specific in the
  last place: an iceberg beside a monument came out differently because
  this aarch64 HotSpot's cosine intrinsic differs from `StrictMath` (and the
  platform's from both) on its angle. The oracles now run with HotSpot's

## VMC-025f6 — start flags between transactions (October 21, 2026)

- The one start state that a later transaction must see is a mineshaft
  spider corridor's flag that it has placed its cave spider spawner
  (vanilla's `hasPlacedSpider`, saved with the start): the spawner goes to
  the first chunk with a free spot, which depends on the order. Temple and
  hut heights are settled the same in every transaction (VMC-025f5), and the
  other once-only placements (chests, a portal room's or fortress throne's
  spawner, a hut's witch and cat) sit at one position, so one chunk places
  them.
- Proto chunks keep the flags (`PlacedOnce`: structure id, start chunk,
  piece index; proto images version 4). Before decorating, a live
  transaction applies the flags of every chunk it holds to the starts it
  made; after, it records each piece that newly placed its spawner in every
  chunk it holds within a chunk of the piece, and those chunks commit with
  the transaction. A corridor spans at most three chunks, so any later
  transaction decorating another of its chunks holds that chunk's 3 × 3,
  which shares a chunk with the setter's 3 × 3: it reads the flag, and the
  two lock sets overlap, so the transactions are ordered. The flags are as
  durable and fenced as the chunks' images, through restarts included.
- Parity: `worldgen_live_structures` gains the regions (0, −2), (1, −2) and
  (1, −1) of seed 20261020, where the mineshaft starting at chunk (8, −8)
  has three spider corridors that each cross from one transaction's
  decorated chunks into the next; without the flags the second transaction
  placed a second spawner (at 152, −44, −111), with them the 192 final
  chunks equal vanilla's. `test/structure_flags_test.exs` checks that
