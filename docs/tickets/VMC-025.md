# VMC-025 — Features and structures

Status: In progress
Milestone: M2 real worlds
Depends on: [VMC-024](VMC-024.md) (terrain through carvers, generated live).

Generated worlds have vanilla's terrain but no trees, plants, ores outside the
veins, lakes, springs, geodes or structures. Vanilla adds them in the features
step (`ChunkGenerator.applyBiomeDecoration`), which decorates one chunk while
its eight neighbours are at least terrain, and may write into all nine. This
ticket brings that step, first as parity-tested foundations, then live.

The 26.3 overworld decorates in 11 steps with 171 placed features (178
features over 33 feature types: 33 tree configurations, 31 simple blocks, 24
ores, selectors, disks, springs, lakes, geodes, dripstone and sulfur
speleothems, vegetation patches, fossils, monster rooms and more) and 13
placement modifiers. 26.3 merged configured features into features (a
feature is a typed record in `worldgen/feature`) and added a
`worldgen/block_state_provider` registry and an explicit placer
(`FeaturePlacer`) that applies placement modifiers depth first.

Behaviour comes from the pinned jar (`javap -c` and the private Vineflower
decompilation recorded in [VMC-023](VMC-023.md), now also the feature,
placement, structure and chunk status packages) and from oracles that run
vanilla's own feature classes. The Rust is original.

Acceptance (parent):

- For several seeds and chunks near and far from the origin, a decorated
  chunk area equals vanilla's block for block (with block entities, fluid
  ticks and post-processing marks) when both decorate the same chunks in the
  same order.
- New worlds generate features and structures live, each chunk decorated
  once, and a vanilla client sees them; nothing is cut off at chunk or region
  borders.
- Decoration throughput is benchmarked against vanilla and Pumpkin on matched
  chunks and stays in Pumpkin's range.

## Design notes

- Order dependence: decorations of neighbouring chunks overlap, so a chunk's
  final contents depend on the order in which its neighbours were decorated.
  Vanilla decorates each chunk once in whatever order its chunk system
  reaches it. Parity is therefore defined for a given order: the oracle and
  ValiMC decorate the same chunks in the same order. Live generation (025d)
  keeps vanilla's invariants (each chunk decorated once, writes only within
  its 3 × 3, a chunk final once its whole 3 × 3 is decorated) rather than
  vanilla's incidental order.
- The decoration oracle cannot build a `WorldGenRegion` without a running
  server, so it implements vanilla's `WorldGenLevel` interface as a proxy over
  proto chunks, following `WorldGenRegion` (write zone, `setBlock`
  post-processing and block entity handling, heightmaps through the proto
  chunks, biomes through `BiomeManager` over the chunks' stored biomes), and
  fails on any method a feature calls that it does not implement. The
  features, placement modifiers and placer are vanilla's own classes.
- The worldgen registries are the ones a server loads from the vanilla data
  pack, not the ones vanilla's code builds (`VanillaRegistries`): the pack's
  JSON is what the code's values encode to, and where a codec writes one
  field from another the two differ. The cherry foliage placer writes its
  corner hole chance from its wide bottom layer hole chance, so the pack (and
  every server) uses 0.25 where the code says 0.5.

## VMC-025a — decoration pipeline and first features (October 20, 2026)

- Facts (stage `worldgen_facts`): `features.json` (240), `placed_features.json`
  (273), `block_state_providers.json` (8), each biome's placed features per
  step in `biomes.json`, and `feature_order.json`: per biome source
  (overworld and nether presets, the End) the placed features of each step in
  the order vanilla's own `FeatureSorter` gives them, whose index seeds each
  feature. `blocks.json` (`WorldgenBlocksOracle`): per state `isAir`,
  `canBeReplaced()`, legacy `isSolid`, `liquid()`, block entities, sturdy
  full faces, post-processing positions (the block itself, or above it for
  soul sand and magma), and liquid, double plant and mossy carpet blocks; a
  state whose sturdiness reads the level (moving piston, shulker boxes) has
  none.
- Survival (stage `worldgen_survival`, `SupportOracle worldgen`,
  `priv/worldgen/survival.json`): decoration checks `canSurvive` before
  placing, so the block's own position is an input like its neighbours (tall
  seagrass needs water there), under the light of unlit chunks (sky 15, block
  0). The oracle derives per-state rules with the support facts' partitions
  and tables (VMC-029c), seeds each cell's search with common states, and
  validates every rule on random neighbourhoods (936,832, all equal): 7,326
  states, 200 rules; chorus plants are excluded (more than eight cells). The
  physics support facts are unchanged.
- `valimc_core::worldgen`:
  - `random`: `WorldgenRandom` over Xoroshiro (the legacy algorithms on
    Xoroshiro's bits, the Gaussian kept across reseeds) with decoration and
    feature seeds; stage `worldgen_random` gains 200 such traces.
  - `providers`: int, float and height providers and weighted lists, shared
    with the carvers.
  - `blocks`: the block registry with properties, tags and the flags above.
  - `region`: proto chunks at status `terrain` (heightmaps primed from the
    terrain; the final four updated on writes, the worldgen two frozen, as
    `ProtoChunk` does; writes into an all-air section skipped for air;
    post-processing marks; ticks stored once per position and type at delay
    0; pending block entities) and the region a chunk is decorated through,
    following `WorldGenRegion`: the 3 × 3 write zone, reads up to the area,
    chunk biomes of the 3 × 3 through the fuzzy zoom.
  - `predicate`, `state_provider`, `placement`: every 26.3 block predicate,
    rule test, block state provider and placement modifier the overworld uses
    (`cuboid` waits for its feature), and `FeaturePlacer` (modifiers depth
    first).
  - `feature`: the decoration registry and `applyBiomeDecoration` without
    structures (decoration seed from the chunk origin, possible biomes of the
    3 × 3, vanilla's feature order and seeds, the biome check against each
    biome's placed features), and the features ore (written straight into
    sections, as vanilla), disk, spring, simple block (double plants with
    waterlogging), the random, simple random, weighted and boolean selectors,
    sequence, block column, lake, freeze top layer, blue ice and block blob.
    Other types parse as unsupported and fail if placed.
  - `Worldgen::decorate_area`, NIF `worldgen_decorate`.
- Stage `worldgen_decoration` (`DecorationOracle`, `check_decoration.exs`):
  for three seeds, five areas each (two near the origin, two within 32,000
  blocks, one far out), the 5 × 5 chunks get vanilla's terrain, the 3 × 3 in
  the middle are decorated in order (Z outer, X inner) by vanilla's own
  features, with every placed feature whose types this slice implements: 115
  of the overworld's 171 (all ores, disks, springs, lakes, flowers, grass and
  other plants, seagrass, sugar cane, cacti, kelp, mushrooms, blue ice,
  freezing). All 36,864,000 blocks, 19,081 post-processing marks, 756
  scheduled ticks and both block entities equal vanilla's; a changed block
  fails. The oracle's level implements `WorldGenLevel` over proto chunks after
  `WorldGenRegion` (lit as unlit chunks are, fluid tags bound as a server
  binds them); with every placed feature included, its loop gives the same
  area as vanilla's own `applyBiomeDecoration`, which the oracle checks on
  its first area.
- Ores take `Math.sin` and `Math.cos` of a float direction (2^24 values).
  `Math` may differ between JVMs within an ulp: this aarch64 HotSpot differs
  from `StrictMath` on 1,884,807 of them, and Rust's platform functions from
  this JVM on 1,658,311 (sine) and 1,191,188 (cosine), always by one ulp. A
  vein can only differ where a coordinate lands within about 1e-15 of a block
  boundary; none did in the parity areas (`DecorationOracle trig` measures
  it).
- Benchmark (`bench/worldgen_decoration.exs`, `DecorationOracle … bench`; one
  thread, seed 20261020, 64 chunks decorated in a 10 × 10 terrain area,
  terrain excluded; raw results in ignored `bench/results/`): the 115 placed
  features take a median 0.48 ms per chunk in ValiMC against 1.14 ms in
  vanilla through the oracle's level. Pumpkin's features stage runs every
  feature and structure, so its comparison waits for VMC-025c.

## VMC-025b — trees and large plants (October 20, 2026)

- Facts:
  - `blocks.json` gains `isSolidRender` and, per direction, a full collision
    face (`Block.isFaceFull` of the collision shape); a face that holds a vine
    or a pale moss carpet is full in its support or collision shape.
  - `shapes.json` (`ShapeOracle`, stage `worldgen_shapes`): what
    `updateShape` does at a tree's edge, per state and direction, as rules
    over the neighbourhood (partitions and tables like the survival facts):
    the new state and the block and fluid ticks it schedules. It covers the
    states of every block the worldgen facts or ValiMC's worldgen code name
    whose class overrides `updateShape`: 1,563 states, 1,507 with rules (2,085
    rules, 555 outcomes), lava included (its tick delay reads the level's
    environment attributes; a proto chunk keeps no delay).
  - Left out, and an error if decoration reaches one: fire (it reads six
    neighbours' flammability; only the Nether's fire patches place it),
    chorus plants (whole stems; only the End has them), states whose update draws
    from the level's random (coral blocks, cave vine, kelp, twisting and
    weeping vine plants), reads scheduled ticks (pointed dripstone, sulfur
    spikes) or the registries (attached stems).
  - Vines and pale moss carpets read up to six cells; their updates are code
    (`multiface`), not facts.
- `javahash`: `HashSet<BlockPos>` in Java's iteration order, including bins
  that become red-black trees (root first in the bin's list, new entries
  linked after their tree parent, resizes splitting and untreeifying as
  `HashMap` does, iterator removals). Trees, fallen logs and vegetation patches
  iterate such sets. Stage `worldgen_random` gains 200 traces of additions,
  removals, iterator removals and orders on clustered positions (199 of them
  make tree bins), equal to the JDK's.
- `tree`: `TreeFeature` with every 26.3 trunk placer (straight, forking,
  giant, mega jungle, dark oak, fancy, bending, cherry, poplar, upwards
  branching), foliage placer (blob, fancy, bush, jungle, spruce, pine, acacia,
  dark oak, mega pine, random spread, cherry, poplar), both feature sizes,
  mangrove roots and every decorator (beehive with its bees' draws, place on
  ground, alter ground, trunk and leaf vines, cocoa, attached to leaves and to
  logs, shelf mushrooms, creaking hearts, pale moss with its moss patch and
  hanging moss); leaf distances (`updateLeaves` over the hash sets) and
  `updateShapeAtEdge` in `forAllFaces` order through the shape facts; and
  `FallenTreeFeature`.
- `plants`: huge red and brown mushrooms (vanilla checks a red mushroom's
  space with tree heights of -1, so only the stem's column) and bamboo with
  its podzol. `feature`: vegetation patches and their waterlogged variant;
  pale moss carpets placed as `MossyCarpetBlock.placeAt` does, drawing from
  the region's random (positional, `worldgen_region_random` at the centre
  chunk).
- Stage `worldgen_decoration`: besides the 15 areas of 025a, 22 areas on seed
  20261020 centred where a biome is at the surface (lush caves at y 0), one
  per tree family: jungle, bamboo jungle, sparse jungle, dark forest, pale
  garden, mushroom fields, both old growth taigas, cherry grove, mangrove
  swamp, savanna, windswept savanna, dappled forest, birch and old growth
  birch forest, swamp, snowy taiga, flower forest, meadow, wooded badlands,
  grove. With 148 of the overworld's 171 placed features (every tree, fallen
  tree, huge mushroom, bamboo and vegetation patch besides 025a's), all
  90,931,200 blocks, 51,057 post-processing marks, 52,052 scheduled ticks and
  6 block entities of the 37 areas equal vanilla's. The 23 left wait for
  VMC-025c.
- Benchmark (`bench/worldgen_decoration.exs`, matched with vanilla, 64 chunks
  at seed 20261020, one thread, terrain excluded): the 148 placed features
  take a median 0.53 ms per chunk in ValiMC against 1.31 ms in vanilla's own
  features. Pumpkin's features stage on the same chunks, decorated in the
  same order (a local harness, as for VMC-024), takes 0.77 ms per chunk; it
  runs all of its features and places structure pieces, so it is a ballpark
  until VMC-025c and the structures, not a matched number.

## VMC-025c — the remaining overworld features (October 21, 2026)

- Facts:
  - `templates.json` (`StructureTemplateOracle`, stage `worldgen_facts`): the 28
    templates the features name (16 fossils, the desert well and its
    suspicious sand, 10 sulfur springs), loaded from the vanilla data pack
    through vanilla's own template source (data fixed), each palette's blocks
    in the order `StructureTemplate` holds them (full blocks, other blocks,
    block entities, each by y, x, z) with block entity SNBT; and the rotations
    and mirrors of the 47 states templates and rule processors place.
    `processor_lists.json`: the `worldgen/processor_list` registry (40).
  - `blocks.json` gains `isCollisionShapeFullBlock`, full face occlusion
    shapes per direction (underwater magma's visibility), and
    `LiquidBlockContainer` and `SimpleWaterloggedBlock` (template
    waterlogging).
  - `shapes.json` also covers the blocks of templates and processor lists and
    the blocks ValiMC's code places (sculk sensors and shriekers): 2,023
    states, 1,906 with rules (3,336 rules, 893 outcomes). Speleothems
    (pointed dripstone, sulfur spikes) read scheduled ticks, so their update
    is code (`speleothem::update_shape`, reading the region's ticks), like
    vines.
- `valimc_core::worldgen`:
  - `speleothem`: `Column.scan`, large dripstone (wind, moving the base into
    stone), speleothem clusters (pools, merged tips) and single speleothems.
  - `formations`: icebergs (an ellipse axis of 0 gives a NaN distance, which
    is outside), ice spikes, geodes (the parity noise of vanilla's
    `NormalNoise.createParity` from a legacy random, cached per seed),
    underwater magma and monster rooms.
  - `sculk`: multiface growth with `MultifaceSpreader` and the sculk vein
    configuration, and sculk patches with the world generation
    `SculkSpreader`, its cursors and the behaviours of sculk, veins and other
    blocks. Vanilla's growth search moves to the same neighbour on every step
    of its range, so only the first step can place.
  - `plants`: root systems (rooted azalea trees and rooted sulfur springs),
    vines, coral trees and claws.
  - `template`: templates, the block rot, protected block and rule processors
    (append-loot modifiers), `StructureTemplate.placeInWorld` (palette draw,
    processing inside the bounding box, rotation, block entities, waterlogging
    and filling, `updateShapeAtEdge` and `updateFromNeighbourShapes`), and the
    template and fossil features; overlays and no-ops in `feature`, the
    cuboid placement modifier in `placement`.
  - `region`: block entities created by `getBlockEntity`, with what features
    write into them (a chest's loot table and seed, a spawner's mob, a
    brushable block's loot from its template); beehives from 025b's decorator
    are now created too. A created block entity survives a block with one
    replacing its block, as `setBlockEntityNbt` keeps it.
  - Random-block providers over a tag draw from the tag's blocks in vanilla's
    order; the biome check keys placed features densely instead of hashing
    their names.
- Oracle: `DecorationOracle` loads the worldgen registries as `WorldLoader`
  does (static registries' tags from the pack first, then applied), since a
  random block of a tag dereferences the tag; its level's server holds a
  structure template manager over the vanilla data pack; it writes, per
  created block entity, its type, loot table and seed and spawned entity.
  Classes read for this slice, besides those of 025a/b (Vineflower 1.12.0 over
  the pinned jar, ignored `research/disassembly/vmc023/src11`–`src14`):
  `MultifaceSpreader`, `SculkSpreader`, `SculkBehaviour`, `SculkVeinBlock`,
  `SculkBlock`, `SpeleothemBlock`, `SpawnerBlockEntity`, `BaseSpawner`,
  `RandomizableContainer`, `BrushableBlockEntity`, `SimpleWaterloggedBlock`,
  `WorldGenRegion`, `BlockScanUtils` and `BoxBlockMatcher`, `BlockPos`,
  `Util`, `Direction`, `WeightedList`.
- Stage `worldgen_decoration`: 13 more areas on seed 20261020: deep dark,
  dripstone caves, sulfur caves, ice spikes, warm ocean; frozen and deep
  frozen oceans where `iceberg_packed` and `iceberg_blue` pass their rarity
  filter in the centre chunk; desert with the desert well, desert and swamp
  with the lower and upper fossils, plains with a geode, likewise; lush caves
  and sulfur caves where a rooted azalea tree and a rooted sulfur spring
  change blocks on their own. With all 171 overworld placed features, the
  oracle's loop equals vanilla's own `applyBiomeDecoration` on the first area,
  and all 122,880,000 blocks, 94,989 post-processing marks, 65,711 scheduled
  ticks and 142 block entities of the 50 areas equal vanilla's, with what the
  features wrote into 26 of them (14 dungeon chests, 8 spawners, the desert
  well's 2 suspicious sand blocks, 2 beehives). The areas place 13 geodes,
  3 icebergs, 7 ice spikes, 59 large dripstones, 75 sculk patches,
  2 fossils, 8 monster rooms, a desert well, a rooted azalea tree and a
  sulfur spring.
- Ores, icebergs and dripstone take `Math` sine, cosine, power and logarithm;
  as in 025a, the JVM's and Rust's may differ within an ulp, which can only
  matter where a value lands within about 1e-15 of a cell boundary; none did.
- Benchmark (`bench/worldgen_decoration.exs`, matched, 64 chunks at seed
  20261020, one thread, terrain excluded; raw results in ignored
  `bench/results/`): all 171 placed features take a median 0.78–0.79 ms per
  chunk in ValiMC against 2.4–2.7 ms in vanilla's own features (two runs
  each). Pumpkin's features stage on the same chunks in the same order takes
  a median 0.83 ms in both runs; it also places structure pieces, so the
  comparison is matched apart from structures. The area's dripstone caves
  account for most of the added time (pointed dripstone and clusters about
  0.18 ms per chunk); ores remain the largest share.
