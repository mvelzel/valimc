# VMC-011a3 — Owner-fenced block batches

Status: Done within owner-local block scope. October 15, 2026. Builds on VMC-014b6a and VMC-011a1.

Add one bounded atomic mutation inside a region owner and replicate section
updates as shared immutable binaries. This gives future simulation a real commit
boundary and avoids one mailbox event/packet per changed block in bulk edits.

Acceptance:

- Prepare at most 4,096 unique valid block positions outside the owner. One batch
  belongs to one region; reject cross-region input and invalid registry states.
- Commit only against the supplied owner incarnation and exact block revision.
  Apply all edits or none, advance the region revision once and invalidate each
  touched chunk once. Capacity/stale failures leave state/publication unchanged.
- Prepare native section-update payloads/compression outside the region. Publish
  one region event with shared frames, filtered by each recipient's loaded chunks.
  No new process/timer, global coordinator or cross-owner atomicity claim.
- Native codec round trips cover signed section coordinates, all local positions,
  state boundaries and packet ordering. Test rejected commits, cache invalidation,
  real compressed TCP updates and separate-owner responsiveness.
- Dedicated actual client sees a multi-block fixture appear and disappear, can
  walk around it and reconnect with clean logs. Keep the snapshot immutable and
  preserve journal/receipt consistency. Run broad checks after this coherent
  tick/admission/batch block, with targeted checks for the individual checkpoint.

Reference: pinned Mojang 26.3 `ClientboundSectionBlocksUpdatePacket`, `SectionPos`
and block-state registry. Ownership/batching follows the BEAM architecture; native
wire behavior does not dictate the storage-region or scheduler design.

Implementation: `Region.set_blocks(owner, revision, edits)` prepares bounded
validated changes and shared compressed frames in its caller. One owner callback
checks epoch/revision/capacity, commits all edits and publishes one batch. Chunk
versions advance once each. Timeout is explicitly uncertain; never blindly retry
an ambiguous commit. Ordinary periodic-save durability is unchanged. This internal
API does not create cross-owner authority or replace single-block interactions.

Checks: five new regressions plus affected observation/world/timer tests (23)
pass, including capacity, stale/wrong owners, compressed TCP visibility and an
independent owner while another is suspended. Native decoding/update callbacks
and byte-identical re-encoding pass for 18 sections / 73,728 updates, including
every local position, signed/extreme coordinates and mixed/registry-edge states.

Microbenchmark: identical air→stone workloads, one owner and fast local subscriber;
preparation/commit/publication included. 4,096 edits use one event/packet and 7,230
framed bytes versus 4,096 events/packets and 49,152 bytes individually. This does
not measure network/client rendering, survival capacity or cross-server speed.
Raw inputs/results/hashes: `bench/results/vmc011a3.json`; reproduce with
`MIX_ENV=test mix run bench/block_batch.exs bench/results/vmc011a3.json`.

Larger tick/admission/batch block: 472 full tests, isolated production release
`.local/ownership-block-build/rel/valimc` and full native integration pass,
including plaintext/encrypted TCP. Formatting, links and public-tree audit pass.
Private logs: `.local/{vmc011a3,ownership-block}-*`.

Dedicated Java 26.3 client passed on frozen `ea86f1b` production code: one 63-edit
batch creates a wall in two chunks (revision 0→1), both visibly render and block
actual movement at z=2.699999988. Stale revision 0 is rejected with no change;
one restore batch returns all originals (1→2), visibly removes the wall and permits
walking through. Cleanup, reconnect, `/stats` and fresh client/server logs pass;
journals/receipts remain consistent. Report: `.local/client-tests/VMC-011a3/report.md`.
The same baseline covers VMC-011a4's planning docs, not its unimplemented features.
