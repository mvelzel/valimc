# VMC-053 — Vanilla commands

Status: In progress
Milestone: M2 real worlds (manual testing); the full set spans M3 onward
Depends on: VMC-002 (command graph); [VMC-010](VMC-010.md) (operators, bans and
the whitelist) for administration.

Players type vanilla 26.3 commands and get vanilla's command tree, completion,
results and messages. Before this ticket ValiMC knew only `/help`, `/stats` and
`/spawn`, and `/tp` answered "Unknown command".

The parent covers vanilla's 92 dedicated-server commands: parsers, entity
selectors, permission levels, suggestions, execution and exact messages. Every
command belongs to one subticket below. Commands whose systems ValiMC lacks stay
Planned or Parked; nothing is advertised that does not run.

## Design

- **One generated tree.** `CommandTreeOracle tree` writes vanilla's dedicated
  dispatcher in registration order to `priv/commands/tree.json`: node types,
  executable flags, redirects, the lowest permission level per node, the
  packet's restricted flag, argument parser IDs with their JSON and network
  properties, and suggestion IDs. Game rule literals are sorted, because vanilla
  keeps them in an identity hash map whose order changes between runs.
  `Valimc.Commands` names the vanilla paths ValiMC executes; `Valimc.Command.Tree`
  keeps those paths, their ancestors and aliases that redirect to them (`tp`,
  `xp`, `tell`, `w`), and encodes one commands packet per permission level, as
  vanilla's `fillUsableCommands` does. ValiMC's `/stats` and `/spawn` stay as
  extra literals. `CommandTreeOracle facts` writes the game rules, timelines and
  time markers to `priv/commands/facts.json`.
- **Brigadier parse.** `Valimc.Command.Dispatcher` follows `parseNodes`: literal
  relevance, the separator check, redirects and potential ranking, then
  `finishParsing` with vanilla's messages and the gray `...text<--[HERE]` context
  that suggests the command on click. Text is read as UTF-16 code units, so
  cursors and contexts equal Java's. Parsing is a pure function.
- **Arguments.** Vanilla syntax and errors for numbers, strings, booleans,
  identifiers, resources and tags, coordinates (`~`, `^`, centring), entity
  selectors with every option, game modes, times, messages with selectors,
  block states and predicates, items and SNBT. Syntax vanilla accepts but ValiMC
  cannot carry out is refused with ValiMC's own red "not supported yet" message
  instead of being approximated.
- **SNBT.** `Valimc.Command.Packrat` is a packrat engine with the semantics of
  vanilla's `util.parsing.packrat`, so vanilla's messages come out unchanged:
  - branch scopes that keep keys when cleared;
  - `cut`;
  - lookaheads that silence only their own terms;
  - per-cursor memoisation that caches failures too;
  - errors kept only at the furthest cursor (`LongestOnly`).

  `Valimc.Command.Snbt` is vanilla's `SnbtGrammar` on that engine. It produces
  numbers with sign, base, underscores and type suffixes, with Java's
  `NumberFormatException` texts, plus strings and escapes, lists, typed arrays,
  compounds and the `bool`/`uuid` built-ins. `Valimc.Command.ItemPredicate` is
  `ComponentPredicateParser` on the same engine.
  - Item components decode for `damage`, `max_damage`, `max_stack_size`,
    `repair_cost`, `unbreakable`, `enchantment_glint_override` and
    `custom_data`, with the codec messages vanilla shows.
  - Item predicates support `count` and component presence or equality.
  - `\N{name}` escapes (Java's Unicode name table), other components,
    predicate types other than `count`, block entity data beyond `{}` and
    selector `nbt=` matching are refused with ValiMC's message.
- **Permissions.** Vanilla levels 0–4. Operators come from `:operators`
  (`VALIMC_OPERATORS`: names or `*`); `mix run` in development makes every player
  an operator. Login sends the permission entity event (24–28) before the graph.
  Selectors need level 2, as in vanilla. The operator list itself is VMC-010.
- **Suggestions.** The client asks the server only for `ask_server` nodes.
  `Valimc.Command.Suggestions` follows Brigadier's `getCompletionSuggestions`:
  the node before the cursor, literals by prefix, and vanilla's resource
  matching (`matchesSubStr`) for time markers and timelines of the clock in use.
  Other argument types suggest in the client, which merges both replies.
- **Execution.** Commands run in the player's connection. Changes to another
  player run in that player's connection through a bounded call
  (`Valimc.Commands.Remote`, 1 s), so feedback reports what the target did; a
  target that does not answer is skipped. Messages follow vanilla's
  `CommandResponseTracker`, `sendSuccess` (gated by `send_command_feedback`) and
  the gray italic `[Name: message]` broadcast to other operators. Command chat
  is unsigned, so `say`, `me` and `msg` are disguised chat bound to vanilla's
  chat types.

### Not feasible yet

These parts of the priority commands need foundations ValiMC does not have, so
they are left out of the graph until those exist:

- `spawnpoint`: players have no personal respawn points; respawn always uses the
  world spawn (VMC-040).
- `summon`: only items and experience orbs exist as entities, and vanilla's
  `summon item` without data spawns nothing. It waits for entities.
- `locate poi`: ValiMC keeps no index of points of interest (beds, job sites,
  portals, bells). `locate biome` works in flat worlds; generated worlds need a
  point biome sampler in the worldgen NIF.
- `setblock … destroy` and `fill … destroy` need the mining drop pipeline from a
  command source.
- Game rules other than `advance_time`, `advance_weather` and
  `natural_health_regeneration` need a durable rule store and their gameplay
  hooks; they are not offered yet.
- `effect give` accepts the 17 effects the game applies (`Valimc.LiveEffects`),
  among them night vision, blindness and darkness, which the client draws;
  others are refused.
- `waypoint` changes the waypoints of tracked entities on the locator bar.
  ValiMC sends no locator bar tracking yet.
- `fillbiome` needs a biome edit in the world NIF, a region log frame for it
  and the `chunks_biomes` resend. `place` needs feature, structure and
  template placement from a command. Both stay out of the graph.
- Text components with `nbt` contents are refused: there is no entity, block
  or storage data to read. `score` contents resolve to empty text because there
  are no scoreboards.
- `particle` encodes the options of `dust`, the block particles (from a block
  state string), the colour particles, `dragon_breath`, `effect` and
  `instant_effect`. Other particles with options, such as `item`, `trail` and
  `vibration`, are refused.
- `dialog show` takes registry dialogs; inline dialog values are refused.

### Known differences

- Teleports send an absolute position; vanilla's relative flags end at the same
  pose but keep velocity on relative axes. `facing` computes the rotation on the
  server instead of sending vanilla's look-at packet.
- `give` drops overflow at the player's eyes without vanilla's forward toss, the
  cosmetic pickup item and the sound.
- `setblock` and `fill` place the given state without adapting it to
  neighbouring shapes (vanilla's non-strict mode), so `strict` and the default
  behave alike.
- `/defaultgamemode` lasts until restart (vanilla writes `server.properties`).
- `/seed` refuses in flat preview worlds, which have no seed.
- Selector `@e` and `@n` select players, the only command-selectable entities.
- `locate structure` finds where vanilla's structure starts are
  (`findNearestMapStructure`, up to 100 grid rings, in Rust:
  `worldgen::structure::locate`); ValiMC does not build structure pieces yet
  (VMC-025f), so nothing stands there. A world created without structures finds
  none, as in vanilla. Flat preview worlds have no structures
  and refuse it. The search runs in the player's connection, which waits for it
  as vanilla's server thread does.
- `posteffect` lists live on the online player and are cleared on respawn as in
  vanilla, but are not saved across reconnects yet.
- `clone` works within the overworld and refuses blocks with block entities
  until their contents can be copied. Like `fill`, it places states without
  neighbour updates, so `strict` behaves like the default.
- `forceload` keeps a saved set of chunks and loads their regions at startup.
  Region owners do not unload yet, so every visited chunk keeps ticking anyway.
- `tick rate` sets the interval of region owners, the world clock and player
  connections. A frozen game stops region game ticks and the world clock;
  `tick query` reports region tick durations.

## Acceptance (each slice)

- The slice's commands are in the client's tree with vanilla's parsers,
  properties, suggestion types, restricted flags and aliases. Mojang's decoder
  reconstructs the graph, and it equals vanilla's usable tree pruned to ValiMC's
  commands at permission levels 0 and 4.
- Parsing equals vanilla's for the corpus in `CommandTreeOracle` (paths and
  argument text, or failure components) at levels 0 and 4.
- Execution results and messages follow vanilla's command classes for the
  covered cases (the tests name them); unsupported parts fail visibly.
- Format, affected tests, the `commands` oracle stage and the public-tree audit
  pass; this ticket and the roadmap say what is live.

Client scenario (VMC-053a–d milestone), as an operator:

- `/` lists the commands, and `/tp`, `/gamemode`, `/give` and `/effect` complete
  arguments locally and execute.
- `/gamemode creativ` shows vanilla's red error with the `<--[HERE]` context.
- `/time set noon` and `/weather rain` change the sky, and `/fill` builds a
  hollow box.
- A second, non-operator client sees only `help`, `list`, `me`, `msg`, `tell`,
  `w`, `stats` and `spawn`.
