# VMC-081g1 — Native random ticks and rule block ticks

Status: Done
Milestone: M3, at the user's request
Parent: [VMC-081](VMC-081.md) (the block-tick half of 081g).

The whole-tick probe of `a75a314c` (VMC-081d's harness, `mobs` scenario,
two pinned cores, 16 simulating sections) spent 1.54 ms of each tick on
random ticks: the sampler NIF took 87 µs per section and Elixir 0.15 ms
filtering its hits. The sampler drew in all 64 chunks of a section, though
about 27 simulate, and Elixir dropped the rest; it scanned every palette
each tick and looked a column up per draw. The rules' random ticks (lava,
growing plants) took another 0.41 ms. In the `explore` scenario the block
phase took 4.3 ms: post-processing and fluid rules on fresh chunks 2.35 ms,
random ticks 1.4 ms.

## Design

- **Vanilla's draws.** `ServerLevel.tickChunk` (pinned jar): for each
  ticking chunk, for each section with `isRandomlyTicking()` (a
  randomly-ticking block or fluid count above zero, `recalcBlockCounts`),
  `randomTickSpeed` positions from `Level.getBlockRandomPos`
  (`randValue = randValue * 3 + 1013904223`, then `val = randValue >> 2`,
  x `val & 15`, y `val >> 16 & 15`, z `val >> 8 & 15`). The chunks come
  from `ChunkMap.forEachBlockTickingChunk` (no shuffle in 26.3; the
  spawning chunks are shuffled, not these). Ice and snow
  (`tickPrecipitation`) and thunder draw from the same generator; ValiMC
  has neither yet.
- **Counts on change.** `valimc_core::random_tick::RandomTicks` keeps each
  section's count of randomly ticking cells (`random_ticking.json`, every
  state vanilla ticks, not only those ValiMC handles), recounted when a
  column is installed or restored and adjusted per cell in `set_many`. A
  tick skips sections with no count without reading their cells.
- **The simulated mask.** The owner passes the simulated, generated chunks
  as the 64-bit mask mob ticks already take; draws happen only there, in
  bit order, sections bottom first, each column looked up once.
- **Decided in the rules run.** Lava's and growing plants' random ticks
  were already the Rust rules engine's decisions; Elixir only split the
  sampler's hits, built actions and paid a second `rule_run` per section.
  Now one run per section and tick does the due block ticks, the fluid
  ticks and then the random phase (`rules::live::RandomPhase`), in
  vanilla's order (`LevelTicks`, then `tickChunks`). A draw reads the cell
  as the run left it so far, so the counts take the run's earlier writes
  into account. Lava's `canSpreadFireAround` is decided natively from the
  players' positions and the game rule's radius; a sapling that grows a
  tree comes back as a position for the generator task. Only the draws of
  the owner's tick behaviours (turtle eggs, budding amethyst) come back as
  cells, and farmland's draws in wet weather, since its tick reads the
  rain above it from the owner's published heights and biomes. A run the
  owner must retry (a busy item plan) drops its random phase, as the
  separate random run was dropped before; a run past the normal scheduler's
  budget leaves the generator where it was for its dirty rerun.
- **Post-processing readiness** looks sibling sections' absent chunks up in
  their set instead of scanning their list (explore spent 33 µs per section
  per tick there).

## Acceptance

- Draws follow `getBlockRandomPos` and skip only sections without ticking
  cells; counts follow edits and installs (`valimc_core` unit tests).
- Region tick, growth (crops, grass, farmland, a sapling's tree), turtle
  egg, fluid (lava's fire near a player), redstone, piston and tick pipeline
  suites pass.
- Vanilla stages: `random_ticking`, `growth`, `fluids`, `turtle_egg_place`,
  `turtle_growth`, then `check_vanilla.py --changed`.
- `mobs`: random ticks at most 0.3 ms per tick.

## Evidence

Whole-tick probe (081x instrumentation), docker, two pinned cores, 60 s,
before `a75a314c`, after `87da98a8` built on it; the host was shared with
other agents' runs (load 12 to 16), so absolute numbers moved by up to 2.5×
between runs of one image. Per tick, ms:

| `mobs` | before 1 | before 2 | after 1 | after 2 |
|---|---:|---:|---:|---:|
| span cost (ns, load) | 156 | 154 | 216 | 105 |
| sampler / mask (Elixir) | 1.370 | 3.265 | 0.091 | 0.129 |
| sampler NIF | 1.245 | 2.807 | — | — |
| separate rules run, Elixir hits | 0.405 | 1.542 | 0.009 | 0.010 |
| native random phase (in the run) | — | — | 0.864 | 0.969 |
| blocks phase | 2.194 | 5.682 | 1.881 | 2.272 |

| `explore` | before | after |
|---|---:|---:|
| sampler + its rules run | 2.500 + 0.868 | 0.083 + 0.006 |
| native random phase | — | 0.846 |
| post-processing | 0.717 | 0.517 |
| blocks phase | 6.986 | 3.893 |

The after images counted every draw and section with shared atomic probe
counters (two per draw, about 11,500 per tick), which inflate the random
phase's span: of its 0.97 ms, the growth ticks took 0.085 ms (75 per
tick), and a release micro-benchmark of the draw loop (27 chunks, every
section ticking, three draws) costs 1 ns a draw, about 9 µs for the 8,676
draws a `mobs` tick makes in 2,900 to 4,500 ticking sections. Vanilla's
counts make far more sections draw than the old palette check did (lava in
caves, leaves, dripstone, vines count though ValiMC handles some of them
only partly), and they are exactly the draws vanilla makes.

Not yet shown: the ≤ 0.3 ms target needs a run without the per-draw
counters; the combined quiet measurement after the 081x slices land is the
gate. Checks: `valimc_core` unit tests; the region tick, growth, turtle
egg, fluid, redstone, piston, tick pipeline and group suites (92 tests);
`check_vanilla.py --changed` 121/121 at the first checkpoint and 119/119
at the second, then `random_ticking`, `growth`, `fluids`,
`turtle_egg_place`, `turtle_growth` and `redstone` on the final tree.
`region_tick_test`'s tick-duration case fails now and then when run beside
other suites (its `ProfileTicks` row is missing); alone it passes.

## Left

- Ice and snow (`tickPrecipitation`) and thunder, which share the
  position generator, are not implemented.
- Farmland's draws in wet weather still go back to the owner for its rain
  check; reading the published heights and biomes natively would remove
  that run.
- Explore's block phase is dominated by committing fresh chunks' fluid flow
  (`commit_rule_changes`, about 290 µs per commit), which belongs to the
  commit path (081h), not to this slice.
